# 性能优化与代码结构化（v5.3.40）

> 用户指令：「在保留应用功能没有任何改变的情况下，想办法优化应用性能。优化方案和方向你自己定。同时尽可能的将应用代码变成一份高度结构化的清晰文本集，可以很轻松的定位、修改、移植、覆盖等操作。」

## 一、先说结论

| 项 | 结果 |
|---|---|
| 性能优化（零功能变更） | **APK 资源减少 6.58MB**，删 5 个无引用文件 |
| 代码结构化 | **符号级索引 26575 个符号 / 1262 个 .kt**，`bin/symbols` 5 秒重建 |
| 新增检测工具 | `bin/perfscan`（零风险性能/体积扫描）、`bin/symbols`（符号定位） |

**诚实交代：这个代码库在「标准性能模式」上已经相当干净** —— 见第二节的实测排除项。

## 二、性能：先排除，再动手

### 2.1 被实测排除的方向（重要 —— 避免做无用功）

| 方向 | 实测结果 | 结论 |
|---|---|---|
| **函数内 Regex** | 145 处 `Regex(`，其中 **131 已在 `val`**；`HardlineCommandGuard` 的 13 个安全正则已是 `private val PATTERNS` | 仅剩 14 处低频，**收益可忽略** |
| **SimpleDateFormat** | 16 处，**全部在低频页面**（设置/日志/错误卡片）；`LogPage` 3 处已用 `remember` | 不在热路径，**不改** |
| **LazyColumn 无 key** | `ChatList` 主列表 **两处都有 `key` + `contentType`**；`ChatDrawer`/`ModelList`/`ToolMatrixPicker` 也都有 | **已是最佳实践** |
| **Markdown 解析** | `MarkdownParseCache` 已是**增量解析**（块级 O(δ)）+ 字符预算 LRU + 跨 tick 节点复用 + 避免全量回退（v4.8.86 深度优化过） | **无空间** |
| **Compose 内集合运算** | message 组件里 7 处，但都是小集合 | 收益 < 风险 |

**结论：传说中「Compose 性能十大坑」这个项目基本都填过了。** 盲目改这些只会引入风险。

### 2.2 真正的收益：死资源（可量化、零功能变更）

`assets/` 曾占 **60MB**（APK 才 85MB）。逐个核对引用方后：

| 资源 | 体积 | 判定依据 | 处置 |
|---|---|---|---|
| `assets/banner/` | **5.10MB** | Kotlin/XML/Manifest **零引用**；真实上游 3.1.1 **已删除该目录** | **删除** |
| `assets/models_dev.json` | **1.48MB** | `ModelsDevCatalog.decode()` **零调用方** —— v5.3.1 只移植了目录类与数据，依赖 ModelRegistry 重构的 `ModelsDevUpdater` 从未移植 | **删除** |
| `res/drawable/patreon.xml` | 小 | 赞助功能已删（v5.0.52），零引用 | 删除 |
| `res/drawable/ic_media_creation.xml` | 小 | 零引用 | 删除 |

**合计 6.58MB。`assets/` 60MB → 54MB。**

保留的（逐个确认过是活的）：
- `assets/rin-tools/` **33.3MB** —— officecli 等文档工具，你日常在用
- `assets/simple_dict/` **13.1MB** —— `SimpleDictManager.extractDict()` 被 `AppDatabaseFactory:55` 调用（FTS 分词）
- `assets/html/` 4.2MB —— mark.html + mermaid（v5.3.17 刚做过 CDN 本地化）

**为什么这算「性能优化」而不是「清理」**：APK 体积直接影响**安装时间、升级下载、冷启动 IO**（资源索引与 dex 同属应用安装包扫描范围），且**零功能变更**是硬约束下唯一可量化的收益。

## 三、代码结构化：从「1353 个文件」到「26575 个可检索符号」

### 3.1 三层索引（已有 + 本轮新增）

| 层 | 工具 | 回答什么问题 |
|---|---|---|
| **文件级** | `bin/origin` | 这个文件是谁的？（UPSTREAM / MODIFIED / PORTED / OURS）+ 能否安全回退 |
| **符号级**（本轮新增） | `bin/symbols` | 这个类/函数在哪？属于哪个类？谁在用它？ |
| **导航级** | `docs/CODE-NAVIGATION.md` | 我要改 X，先看哪几个文件？ |

### 3.2 `bin/symbols` —— 26575 个符号的定位表

```bash
./bin/symbols build          # 重建索引（5 秒）→ docs/SYMBOLS.tsv
./bin/symbols find saveConversation
./bin/symbols uses MemoryRepository
./bin/symbols stats          # 按来源/类型统计
```

实测输出：
```
名字                类型    所属                来源        位置
saveConversation    fun    ChatService.       MODIFIED    ChatService.kt:1704
saveConversationAsync fun  ChatVM.            MODIFIED    ChatVM.kt:666
```

**索引能力**：
- **26575 个符号 / 1262 个 .kt**，**71% 有明确所属类**（其余是真正的顶层函数/属性）
- 每个符号带 **来源分类**（UPSTREAM 12899 / MODIFIED 7545 / PORTED 3659 / PORTED-MODIFIED 1942 / OURS 530）
- 输出 **纯 TSV**，可直接 `grep`/`awk`/`sort`，也可被任何工具消费 —— 这是「清晰文本集」的实际形态

**为什么要有「所属类」**：第一版只索引顶层声明，`find saveConversation` 返回「未找到」（业务方法几乎都是成员函数）→ 索引等于不可用。加 `parent` 列后才有定位价值。

### 3.3 `bin/perfscan` —— 把本轮的排查方法固化

```bash
./bin/perfscan          # 全部
./bin/perfscan assets   # 体积/死资源（最可量化）
./bin/perfscan hot      # 热路径模式
```

**它是清单工具不是门禁**（退出码恒 0）：每一项都给出「为什么可疑」和「零变更的改法」，由人决定改不改。**避免「扫出 100 条就机械全改」这种制造风险的做法。**

## 四、诚实边界

1. **APK 体积收益是估算**：按资源原始体积 6.58MB 计，实际 APK 减少取决于压缩率（图片本就是压缩格式，接近 1:1）。**需 CI 产物实测确认**。
2. **本轮没有做「运行时性能优化」** —— 因为第二节的实测排除了所有标准热点；在没有 profiling 数据的情况下改 Compose/markdown 是**引入风险而非优化**。
3. **未做安装实测**（沙箱无设备）。
4. `bin/symbols` 的 「71% 有归属」不是缺陷：`fun` 中约 29% 是**真正的顶层扩展函数**（如 `Settings.findModelById`），它们本来就没有所属类。
5. `ModelsDevCatalog` 类**保留**（只在注释里写明「要启用必须把 json 放回来」）—— 删类会让将来移植 `ModelsDevUpdater` 时重写解析层。

## 五、下一步（有 profiling 数据时再做）

1. **冷启动耗时**：用 `adb shell am start -W` 量 `TotalTime`，再决定是否值得拆启动链。
2. **Compose 重组计数**：`Layout Inspector` 的 recomposition counts，只改「数字异常高」的组件。
3. **列表滚动掉帧**：`adb shell dumpsys gfxinfo <pkg> framestats`，只看 janky frames 集中在哪个页面。

**在没有这三项数据之前，任何「Compose 优化」都是猜。**
