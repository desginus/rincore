# 预热管线 (铺展瞬时高负载) — 设计文档

版本: v4.8.50 起 | 用户定版架构 (2026-09-26)

## 背景与问题

渲染/准备类工作存在"一瞬间高负载, 之后空跑"的形态: 例如进入对话瞬间的
集中解析、启动后的冷启动成本。目标: 把瞬时高负载**铺展开**, 用时间、空间
换体验与效能; 解决不完的准备结果**沉淀进存储**, 跨进程复用。

## 硬性约束 (用户定版)

1. **渲染连续性零破坏**: 可见行为与 4.7.26 原版形态完全一致 (首帧即终态,
   无占位/无渐进替换/无跳变)。铺展的是"准备"(解析缓存填充), 不是"显示"。
2. **绝不复用"追赶线"机制** (已整体删除, 永不复用): 禁止任何"根据上一轮
   耗时/速度决定下一轮节奏"的自适应节流、"单飞行延迟上屏"、"合并窗口延迟
   更新"、"检查点分批"等调度层实验。该研究线 (4.8.36-4.8.41) 已零残留。
3. 分时切片: 批间让渡, 防 CPU 突发; 生成中自动避让 (不抢占流式 CPU)。
4. 不再开倒车: 功能只进不退; 本管线后续迭代只做增量。

## 三层结构 (v4.8.50 已实现)

```
① 启动预热   WarmPipeline.startOnAppStart()   [RikkaHubApp.onCreate 挂点]
   └ 延迟 2.5s (让启动链/首屏先行) → 最近对话最新 160 条正文分时解析

② 会话进入预热 WarmPipeline.warmAround()      [ChatPage LaunchedEffect]
   └ 进入后延迟 400ms → 以当前位置为中心 ±80 条分时预热

③ 滚动补热   snapshotFlow(滚动停稳, debounce 1.2s) → 对新位置 ±80 条重铺
   └ collectLatest 覆盖旧请求; Mutex 全链单飞
```

参数 (WarmPipeline.kt 顶部常量): WINDOW=80 / STARTUP_MESSAGES=160 /
BATCH=12 / BATCH_GAP_MS=35 / STARTUP_DELAY_MS=2500。

写入目标: `MarkdownParseCache` (LRU 256) — 界面首帧逻辑不变, 命中即零解析。

## 存储沉淀阶段 (Phase 3, 待实现)

"解决不完的, 就放在存储里面" — 对分时也来不及的准备结果做持久化:

- 候选物: 消息正文的解析结果 (AST) 或中间产物 (preprocessed + hasHtml + html)。
- 手段: content-hash 键的磁盘 LRU (filesDir/warm-cache), 启动预热时优先读盘
  回填内存缓存, 未命中再解析。
- AST 序列化可行性: vendored `:markdown` 模块为我方代码 (ASTNode/
  CompositeASTNode/LeafASTNode), 可在模块内加编解码器实现完整跳过解析;
  若过重则退化为持久化 preprocessed+html 的中间形态 (跳 preProcess + HTML 生成)。
- 验证: 冷启动 (刚装包) 下进入长对话的首帧, 对比 存储命中 vs 未命中 的每轮
  滚动流畅度; 测试须按"热态协议"判读以免冷态污染。

## 验证协议 (全局, 强制)

版本 A/B 对比必须在**热态**进行: 安装后充分使用 (反复滑动至手感稳定),
再判读体验; 刚装完的冷态读数不得作为回归依据 (2026-09-26 教训)。
