# RinCore 版本管理规范

> 目的：每个版本"改了什么/为什么/后果/教训"完整可追溯；避免重复踩坑（历史教训见 rincore-changelog"历史教训"区）。

## 一、版本号规则

- 格式 `X.Y.Z`：X=大版本（架构级，用户决策），Y=中版本（功能/回滚期），Z=小版本（bug 修复/小改动）
- **小修改/bug 修复默认只升 Z**（如 3.9.1 → 3.9.2）
- **每次版本号变更必须同步递增 versionCode**（当前 204，每次 +1）
- 大版本/用户明确指定时按用户要求走（如用户指定 3.9.0 主线）
- 功能边界：只做用户点名的功能；产品线未经用户确认不建（D18）

## 二、发布流程（铁律）

```
改代码 → 本地自查 → 用户确认 → 推送 → CI 绿 → 提供 artifact 直链
```

- **推送代码 ≠ 交付 APK**：用户只能测试 APK，必须等 CI 绿 + artifact 直链
- **禁止绕道**：不走 daily-build/Prerelease 交付（用户明确否定过）
- **默认不推送**：除非用户明确授权
- **每次改动必须记录**（见下）——不允许"改完不记录"

## 三、记录要求（每个版本必填）

每次版本提交必须包含（写入 rincore-changelog）：

1. **改了什么**（文件级 + 行为级）
2. **为什么改**（用户报告/自查/根因）
3. **后果/影响**（已知副作用、缓存/协议/性能影响）
4. **回滚记录**（如果可能回滚：回滚到哪个版本/基线）
5. **教训**（如果踩坑：是什么坑、如何避免重踩）

## 四、"要改就整个改，不打补丁"

- **禁止补丁式修复**：同一问题反复打补丁 → 回滚到已知稳定基线，从基线重做
- **改动前评估影响面**：涉及缓存/协议/消息结构时，先查"历史教训"区（如 limitContext↔缓存）
- **关联改动一起做**：改动 A 影响 B 时，A+B 一起评估一起改，不留半吊子状态
