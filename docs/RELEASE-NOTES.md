## RinCore v5.3.34
★★★「快速/极致选最快模型」重做：原来的竞速测的根本不是模型速度，而且每次发送都在首字前白等最多 1.5s 🎯**你的怀疑是对的：这套选择逻辑原来基本没起到作用，还有几处是反向作用。**下面先说它原来到底在做什么，再说改成什么。 **━━ 一、原来的「竞速」测的是什么？（代码级）━━** `ModelRacer.race()` 对池内每个模型所属 provider 的 **`GET {baseUrl}/models`** 打一次请求，谁先返回谁赢。**问题在于这个端点与模型推理毫无关系**： **① 测的是「连接建立 + 元数据端点首包」，不是「模型首字」。** 真正的首字延迟 = DNS+TCP+TLS + 请求排队 + 模型 prefill + 首 token，其中**大头（排队/prefill）完全不在 `/models` 里**。小模型比大模型快几百毫秒，这个探针一点都测不出来。 **② 同一 provider 的多个模型，探针打的是同一个 URL。** 你池里若配了 3 个 opencode.ai 的模型 → 3 个探针并发打**同一个 `/models`** → 谁先返回纯属**竞态噪声**（甚至取决于谁先拿到连接池里的空闲连接）。「同 provider 内选最快」这个说法**在结构上就不成立**。 **③ 1.5 秒同步超时，移动网上常常全部超时。** `resolveRoutedModel` 传的是 `timeoutMs = 1500`，而实测 TLS 握手就 664ms~1.9s（蜂窝网更慢）→ **多数情况下所有探针都超时 → 回退到池首**。也就是说：**既没选出最优，又在首字前白等了最多 1.5 秒**。 **④ `checkOverwrite = false` → 测的 host 可能不是用的 host。** 主链路（ChatService / GenerationHandler）全部用默认 `checkOverwrite = true`；只有 ModelRacer 传了 `false`，**忽略 `model.providerOverwrite`** → 配了覆盖 provider 的模型，探针打的是原 provider、主请求走覆盖后的 provider。**选出来的「最快」与真实请求无关。** **⑤ 缓存只有一个槽位。** `private var cache: CacheEntry?` —— 「快速池」和「极致池」交替使用会互相覆盖，频繁 miss。 **━━ 二、GitHub 调研结论：客户端侧没有更好的开源方案 ━━** 查了 GitHub API：`lm-sys/RouteLLM`（★5.6K）、`rohansai/nvidia-litellm-router`（LiteLLM 社区版）等都是**服务端网关**方案；OpenRouter 的 `:nitro`/`:floor` 同样是**服务端**替你选。**没有可以直接搬进本地 App 的多模型竞速库。** 但 LiteLLM 的 `latency-based-routing` 给了关键启发：**它是用「历史响应时间」路由，不是每次发探针**。这正是客户端该做的事 —— 我们自己就有最准的数据：**每次真实请求的首字耗时**。 **━━ 三、改成什么（重新设计）━━** **核心：不再猜，用真实统计。** 新增 `ModelLatencyStats`（纯内存、零依赖、可失败旁路）： - **记录**：ChatService 收到本轮**第一个** `GenerationChunk` 时，记 `当前时间 − 请求发起时间`（这就是用户感知的首字延迟）； - **聚合**：每个模型保留最近 **5 次**样本做平均（网络会变，旧样本不该永远主导）； - **选择**：`resolveRoutedModel` 读统计 → **有样本选历史最快，无样本用池首**； - **零阻塞**：不再在发送前跑任何探针；连接预热丢进 `AppScope + Dispatchers.IO` 后台（fire-and-forget）。 **配套三处修正**：①`checkOverwrite = false → true`（与主请求同 host）；②缓存改 `Map<poolKey, entry>`（快速/极致互不覆盖）；③`prefetch` 从「resolveRoutedModel 里直接 await」改成**真后台** —— 这一步是我自己差点埋的雷：`prefetch` 是 suspend 且内含最长 5s 探针，直接调用会把「零阻塞」又变回阻塞，只是换了个名字。 **━━ 四、新行为的正确预期（不要期待错）━━** · **第 1 轮**：池内都还没样本 → 用**池首**（这是合理的：没有任何信息时不该瞎猜），同时后台开始预热连接； · **第 2~3 轮**：样本积累起来后，自动切到**实测最快**的那个； · **网络变化后**：样本窗口滚动（5 次）会自动跟上，不需要手动重置； · **重启应用后**：内存统计清空 → 重新学习 3~5 轮（**刻意不落盘**：避免 DataStore 迁移风险，且换网络后旧数据本来就不该长期有效）。 **━━ 五、本地验证（这次没拿 CI 当第一验证器）━━** 用 `kotlinc` 编译**真实 `ModelLatencyStats.kt`**（补 `android.util.Log` stub）+ 11 项语义断言，**全部实跑通过**：无样本返回 null / 单候选不竞速 / 快者胜出且顺序无关 / 无样本候选不参与比较 / **窗口滚动 5 次后平均从 1000ms 正确变成 100ms** / 异常值（0、负数、>5min）全丢弃 / 平均值正确 / clear 归零 / **三模型模拟（1800/420/190ms）选中 190ms 那个**。另：`rc check` 双 PASS、`audit fast` = AUDIT-OK、tree-sitter 四文件 PASS、新单测已加入**白名单硬门禁**（`ModelLatencyStatsTest`，8 条用例）。 **━━ 六、诚实边界 ━━** ①**只有主对话链路记样本**；子代理/做梦整理/压缩不记（它们不走 `resolveRoutedModel`，也不该影响主模型选择）。②**没有安装实测** —— 沙箱没有你的设备与 API key；「首字零等待」是代码结构保证（`resolveRoutedModel` 里已无任何网络调用），「选得准」需要你跑几轮后看日志确认。③**日志**：`adb logcat -s ModelLatency` 会打 `record <modelId前8位> ttfb=XXXms avg=YYYms`，`ModelRacer` 的 `race winner=` 现在只用于后台预热、不再参与选择。 **★版本纪律**：5.3.33 → **5.3.34**（只改第三位）。**★改动 6 文件**：`ModelLatencyStats.kt`（新增）/ `ModelLatencyStatsTest.kt`（新增，白名单门禁）/ `ModelRacer.kt`（checkOverwrite + 缓存 Map）/ `SettingsExt.kt`（resolveRoutedModel 重写 + 真后台预热）/ `ChatService.kt`（TTFB 记录点）/ `build.yml`（测试白名单）。 **★待你验证**：①选「快速」连发 3~4 轮 → `logcat -s ModelLatency` 应能看到每轮的 `ttfb` 与 `avg`；②第 2 轮起应该明显不再出现「发送后先卡一下」；③如果池里有明显更快的模型（比如小模型 vs 大模型），第 3 轮后应该稳定选中它（看 `avg` 排序）；④切回普通模型后 `modelRouting` 应归 0（v5.1.5 已修）。 ⑩hub=v5.3.34
