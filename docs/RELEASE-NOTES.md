「新一轮回复被塞进上一个气泡」结构性根修：node 分支只能同 role ①★用户原话："我发送了一条消息，模型想了一会，然后我第二次发送过去，按照正常逻辑来讲，我发送过去应该是重新发送，然后模型重新回复。但现在却变成了模型在先前回复的结果下面继续思考。" + "这bug怎么越改越多了？给我找个合适的基准（4.8.190/5.0.12/3.1.0），把这么多莫名其妙越改越多的bug解决掉。" ②★基准对照结论（逐字 diff，回答"到底从哪开始坏"）：Conversation.updateCurrentMessages **与 4.8.190 逐字相同**；ConversationSession.setJob/getJob **逐字相同**；dispatchNextQueuedMessage 除新增 isReady 自愈分支外相同；messageQueue.pause/resume 调用点数量相同（7/7）。→ **这个 bug 不是"我改坏了基准实现"，而是基准实现里一个从未被正视的边界情况被我们的消息队列放大了**。 ③★真根因（唯一一条代码路径）：Conversation.updateCurrentMessages 的 else { newMessages.add(message) } —— 它的语义是"同一 node 的新分支（重新生成）"，但**没有校验 role**。一旦 chunk.messages 与 messageNodes 的 index 在"队列派发窗口"内发生错位（新 user 消息刚追加/正在追加时，正在流式的 job 仍用它挂起点之前读到的列表），user/assistant 就会被追加进**上一个轮次的气泡**，且 selectIndex 指向新分支 → 用户看到的就是"模型在先前回复的结果下面继续思考"。 ④★修复（不变量，不是补丁）：**一个 node 的分支只可能是同一轮的不同版本，role 必须相同**。新增 appendAsNewNodes 收集器：if (existing != null && nodeRole != null && nodeRole != message.role) { appendAsNewNodes.add(message.toMessageNode()); return@forEachIndexed }，遍历结束后统一 newNodes.addAll(appendAsNewNodes) 追加到末尾（保持时间顺序）。同 role 的 regenerate 分支行为**完全不变**。 ⑤★为什么越改越多（结构性回答，诚实）：全部会话类事故集中在 3 个函数 —— saveConversation / updateCurrentMessages / dispatchNextQueuedMessage，这三个函数累计被改 15+ 次，每次都在**同一个判据上叠加条件**修某一类症状；而同一个判据同时是另一类问题的保护（例如为防"旧快照覆盖"收窄写入，就吞掉"合法的第二轮消息"）。**没有回归测试**，CI 只验能编译，唯一验证者是用户。本轮的修法刻意避开继续叠条件，改为**语义不变量**（分支必同 role）。 ⑥★仍需用户协助定位的部分（诚实）：如果修复后仍出现"合并到上一个气泡"，说明是**整体 index 错位**（例如 messages 缺少开头的 system/占位导致所有 role 都顺移），这种情况静态无法唯一确定；请提供 adb logcat -s ChatService ConversationSession ChatVM 的输出 + 精确操作序列（是否在模型思考中就发第二条、是否用了队列面板取消等）。 ⑦版本矩阵：hub=v5.1.21
