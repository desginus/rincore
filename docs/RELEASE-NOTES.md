★★性能（零功能变更，-6.58MB）+ 代码结构化（26575 个符号可检索）📐**这一轮先说一件可能不像「优化」但更诚实的事：我把标准性能热点逐项实测排除了。** **━━ 一、被实测排除的方向（避免做无用功）━━** | 方向 | 实测结果 | 结论 | |---|---|---| | 函数内正则 | 145 处 `Regex(`，**131 已在 `val`**；`HardlineCommandGuard` 的 13 个安全正则已是 `private val PATTERNS` | 只剩 14 处低频，收益可忽略 | | `SimpleDateFormat` | 16 处**全在低频页面**（设置/日志/错误卡片），`LogPage` 3 处已 `remember` | 不在热路径 | | `LazyColumn` 无 key | `ChatList` 主列表**两处都有 `key` + `contentType`**；抽屉/模型列表/工具矩阵也都有 | **已是最佳实践** | | Markdown 解析 | 已是**增量解析**（块级 O(δ)）+ 字符预算 LRU + 跨 tick 节点复用 + 避免全量回退（v4.8.86 深度优化） | 无空间 | | Compose 内集合运算 | message 组件 7 处，但都是小集合 | 收益 < 风险 | **结论：所谓「Compose 性能十大坑」，这个项目基本都填过了。** 在没有 profiling 数据的情况下改这些，是**引入风险而不是优化** —— 我没做。 **━━ 二、真正的收益：死资源（可量化、零功能变更）━━** `assets/` 曾占 **60MB**（APK 总共才 85MB）。逐个核对引用方后： | 资源 | 体积 | 判定依据 | |---|---|---| | `assets/banner/` | **5.10MB** | Kotlin/XML/Manifest **零引用**；真实上游 3.1.1 **已删除该目录** | | `assets/models_dev.json` | **1.48MB** | `ModelsDevCatalog.decode()` **零调用方** —— v5.3.1 只移植了目录类与数据，依赖 ModelRegistry 重构的 `ModelsDevUpdater` 从未移植 | | `patreon.xml` | 小 | 赞助功能已删（v5.0.52），零引用 | | `ic_media_creation.xml` | 小 | 零引用 | **合计 6.58MB，`assets/` 60MB → 54MB。** **逐个确认过是活的、保留的**：`rin-tools/` **33.3MB**（officecli 文档工具，你日常在用）、`simple_dict/` **13.1MB**（`SimpleDictManager.extractDict()` 被 `AppDatabaseFactory:55` 调用，FTS 分词必需）、`html/` 4.2MB（mark.html + mermaid，v5.3.17 刚做过 CDN 本地化）。 **为什么这算「性能」而不是「清理」**：APK 体积直接影响**安装时间、升级下载量、冷启动资源扫描**；在「功能零变更」这条硬约束下，它是唯一可量化的收益。 **━━ 三、代码结构化：从「1353 个文件」到「26575 个可检索符号」━━** **三层索引（文件级 → 符号级 → 导航级）**： | 层 | 工具 | 回答什么 | |---|---|---| | 文件级 | `bin/origin` | 这文件是谁的（UPSTREAM/MODIFIED/PORTED/OURS）+ 能否安全回退 | | **符号级（本轮新增）** | **`bin/symbols`** | 这个类/函数在哪、属于哪个类、谁在用 | | 导航级 | `docs/CODE-NAVIGATION.md` | 我要改 X，先看哪几个文件 | **`bin/symbols` 实测**： ``` symbols build          # 5 秒重建 → docs/SYMBOLS.tsv symbols find saveConversation symbols uses MemoryRepository symbols stats ``` 输出： `saveConversation   fun   ChatService.   MODIFIED   ChatService.kt:1704` **26575 个符号 / 1262 个 .kt，71% 有明确所属类**（其余是真正的顶层扩展函数，本来就没有所属类）。每个符号带**来源分类**（UPSTREAM 12899 / MODIFIED 7545 / PORTED 3659 / PORTED-MODIFIED 1942 / OURS 530）→ **改一个函数之前，先知道它是原版的还是我们写的**。 输出是**纯 TSV**，可直接 `grep`/`awk`/`sort`，也能被任何工具消费 —— 这就是你要的「清晰文本集」的实际形态。 **第一版只索引顶层声明，`find saveConversation` 返回「未找到」**（业务方法几乎都是成员函数）→ 索引等于不可用；加「所属类」列后才有定位价值。 **━━ 四、`bin/perfscan`：把这轮的排查方法固化 ━━** ``` perfscan            # 全部 perfscan assets     # 体积/死资源（最可量化） perfscan hot        # 热路径模式 ``` **它是清单工具不是门禁**（退出码恒 0）—— 每项都给出「为什么可疑」和「零变更的改法」，由人决定改不改。**刻意不做「扫出 100 条就机械全改」**，那只会制造风险。 **━━ 五、诚实边界 ━━** ①**APK 实际减少需 CI 产物确认** —— 6.58MB 是资源原始体积，图片本就是压缩格式，接近 1:1 但非精确。②**本轮没有做运行时性能优化**，因为第二节的实测排除了所有标准热点；**没有 profiling 数据时改 Compose 是碰运气**。③**无安装实测**（沙箱无设备）。④`ModelsDevCatalog` 类**保留**（注释写明「要启用必须把 json 放回来」）—— 删类会让将来移植 `ModelsDevUpdater` 时重写解析层。 **━━ 六、下一步（有数据再做，不猜）━━** ①冷启动：`adb shell am start -W` 看 `TotalTime`；②重组计数：Layout Inspector 的 recomposition counts，只改数字异常高的组件；③滚动掉帧：`adb shell dumpsys gfxinfo <pkg> framestats`，看 janky frames 集中在哪个页面。 **这三项数据拿到之前，任何「Compose 优化」都是猜。** **★版本纪律**：5.3.39 → **5.3.40**（只改第三位、不进位）。**★改动**：删 5 个死资源（`assets/banner/` 3 图 + `models_dev.json` + 2 drawable）+ `ModelsDevCatalog.kt` 加注释；**零 Kotlin 逻辑改动**（功能绝对不变）。 **★待你验证**：①APK 体积应从 85.09MB 降到 **~78.5MB**；②启动、聊天、文档处理一切照旧（本轮没动任何逻辑）；③`bin/symbols find <任意函数名>` 应能直接定位到文件与所属类。 ⑩hub=v5.3.40
