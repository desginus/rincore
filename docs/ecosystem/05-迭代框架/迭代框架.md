# 迭代框架

更新日期：2026-08-06
用途：每次迭代开始前必读。定义开发流程、版本管理、快速查找、AI 协作规范、未来扩展方向。

## 一、开发流程（铁律，每次迭代必须走完）

```
1. 定位    用户反馈问题 → 查 04 错误对照表（是否已修/已知根因）
2. 对比    查 01 来源归档 + git log：问题首次引入版本 → 对比上一版本
           连接行为参照 v2.9.8，缓存参照 v3.5.11，原版行为参照 upstream-try/master
3. 澄清    确认触发条件、影响范围、是否与已知决策冲突（decisions skill）
4. 规划    整体考虑：连接机制 + 缓存机制 + 拼装机制 + 收尾链路，禁止只改一段
5. 修改    按 02 模块地图标注的约束修改，请求体零改动原则
6. 验证    本地编译 + 逻辑自查（改了什么/影响什么/边界条件）
7. 推送    用户明确授权 → push → CI 绿 → 提供 artifact 直链
8. 记录    03 修改全记录 + changelog skill + bug-record skill 同步更新
```

## 二、版本管理

- 版本号：前两位锁定，只能递增第三位（v3.5.x）
- versionCode 与版本对应（v3.5.17 → 持续递增）
- 所有查询到的版本控制做好：哪个版本改了什么、修了什么、发生了什么
- 推送清单：改 → 本地验证 → 用户确认 → push → CI 绿 → artifact 直链（7 天保留）
- 推送 ≠ 交付 APK，用户只能测试 APK

## 四、AI 协作规范（高度适配 AI 修改）

1. 修改前必须加载：project-brief（架构基线）+ bug-record（历史根因）+ 本框架
2. 修改必须标注：文件、函数、改动原因、影响范围（在 commit message 和代码注释）
3. 每个关键决策写入 decisions skill，防重复论证
4. 每次修复写入 bug-record，防重复诊断
5. 禁止猜测：无证据不推进，先查文档/代码/日志
6. 禁止静默：中断必须可见，失败必须报错
7. 一次只解决一个根因，禁止顺手改无关代码
8. 改完必须自查边界：中断、取消、超时、空值、并发

## 五、模块化原则

- ai 模块：传输层纯逻辑，不依赖 Android 环境，可独立测试
- app/data：数据与业务逻辑分离
- app/ui：状态驱动，不直接操作数据层
- 服务层：编排逻辑集中，收尾必须 NonCancellable
- 新增功能优先放独立包（如 workflow/ecosystem/subagent），不塞进既有大文件

## 七、已知约束（勿违反）

- 不覆盖本地文件，移植需手动适配架构
- 不改变落盘（持久化）机制
- 能用原版就用原版，在原版基础上做适配
- 测试环境固定：DeepSeek V4 Flash + Chat Completions API 流式
- 用户测试环境设备侧权限已全部满足，不接受以用户侧原因搁置
