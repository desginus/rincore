# 上游移植接口

> 为原版 RikkaHub (rikkahub/rikkahub) 后续更新预留的快速移植通道。
> 目标: 上游出新版本后, 一条命令看清"上游改了什么 + 哪些能直接合 + 哪些要手动",
> 不再从头翻 diff。

## 快速开始

```
python3 scripts/upstream-check.py
```

输出四段:

1. fetch 结果
2. 锚点..最新 之间的上游提交列表
3. 每个提交的改动文件按三类分类:
   - A 直接合并 — 该文件我们从未改动, 可安全采用上游版本
   - B 手动合并 — 我们改过该文件, 需逐行 diff 重放自研修改 (冲突高发文件单独标注)
   - C 评估移植 — 上游新增文件, 按需单独移植
4. 移植建议 + 禁止跟随清单

## 锚点机制

- 锚点文件: docs/ecosystem/06-原版兼容/移植锚点.md 的 `last_synced`
- 每轮移植完成后, 把 last_synced 更新为最新已处理的上游提交
- 下次运行脚本自动从锚点开始, 只差新提交

## 手动流程 (脚本结果之后)

1. **A 类文件**: `git checkout upstream-try/master -- <文件>` 直接采用
2. **B 类文件**: `git show <上游sha> -- <文件>` 逐个 diff, 保留我们的自研修改,
   只取上游的 bug 修复; 冲突高发文件清单见 原版兼容.md 第四节
3. **C 类文件**: 对照 docs/ecosystem/02-模块地图/ 决定是否移植, 按模块隔离原则放新文件
4. **回归测试**: 连接/缓存/工具域/MCP (自研区) + 首条 system 协议 + 请求体结构
5. **收尾**: 更新移植锚点.md + 03-修改全记录 + changelog

## 禁止跟随 (自研保护, 上游出现以下改动一律否决)

- HTTP/2 协议优先 (我们的 DataSourceModule 是 HTTP/1.1 only + keepalive 60s)
- 静默恢复/主动断开 (已证明是中断元凶)
- limitContext 滞回策略 (破坏 DeepSeek 前缀缓存, 见 Message.kt 注释)
- BEFORE_SYSTEM_PROMPT 注入隔离改动
- 请求体动态化 (破坏缓存)
- 落盘机制变更
