# 原版兼容策略

更新日期：2026-08-06
目的：预留 RikkaHub 上游更新兼容能力，让 RinCore 可持续跟随原版演进，同时保护自研修改不被上游覆盖。

## 一、上游关系

```
rikkahub/rikkahub (原版上游, 当前 2.4.5)
    ↑ remote: upstream-try (rincore-src 中)
    │
desginus/rincore (RinCore, 当前 3.5.17)
    ├── 直接 fork 自原版
    ├── 传输层回滚至 3.2.2 基线（原版移植前）
    └── 大量自研：域分类/动态工具/缓存/连接加固
```

本地 remote 配置（rincore-src）：
- origin: desginus/rincore（本项目）
- upstream: desginus/RikkaHub（个人 fork，已停用）
- upstream-try: rikkahub/rikkahub（原版，活跃跟踪）

## 二、兼容原则

1. 能用原版就用原版，在原版基础上做适配
2. 自研代码与原版文件尽量隔离（新文件、新包），少改原版文件
3. 必须修改的原版文件集中在传输层和生成链路，其余尽量保持原版
4. 每次上游更新，先对比影响面再决定是否合并

## 三、上游更新合并流程

```
1. 拉取    git fetch upstream-try
2. 对比    git log upstream-try/master..origin/main（我们的独有改动）
           git log origin/main..upstream-try/master（上游新改动）
3. 分类    上游改动文件分三类：
           A. 我们未改动的文件 → 直接合并（无冲突）
           B. 我们改过的文件 → 逐文件 diff，手动合并自研部分
           C. 上游新增功能 → 评估是否需要，需要则单独移植
4. 测试    合并后重点回归：连接/缓存/工具域/MCP（我们的自研区）
5. 记录    合并内容写入 03 修改全记录 + changelog
```

## 四、冲突高发文件（我们深度修改，上游更新需重点处理）

## 五、上游新版本检查清单

1. 协议设置：是否重新引入 HTTP/2 优先（必须否决）
2. 传输层：是否引入静默恢复/主动断开（必须否决）
3. 缓存：是否引入 limitContext 类滞回策略（必须否决）
4. 请求体：是否改变 system/tools 结构（评估缓存影响）
5. 消息序列：是否违反首条 system 协议
6. 落盘机制：是否改变持久化（不跟随）
7. 新功能：MCP/工具/UI 增强按需移植

## 六、禁止跟随上游的修改（自研保护）

- 连接协议配置（HTTP/1.1 only + keepalive 60s）
- 静默恢复/主动断开相关（已证明是中断元凶）
- limitContext 滞回策略
- 注入隔离（BEFORE_SYSTEM_PROMPT 独立消息）
- 请求体动态化（破坏缓存）
- 落盘机制变更

## 七、版本对照锚点

- 原版 2.4.5 = upstream-try/master 8349ef25（归档：01-来源归档）
- 传输层基线 = v3.2.2（域分类白板化）
- 连接参照 = v2.9.8（SSE 重试）
- 缓存参照 = v3.5.11（SystemPromptBuilder）
- 干净基线 = v3.5.3（70K 根治后）
