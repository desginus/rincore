# 主流模型请求体格式调研 (2026-08-27)

## 结论总览
| 模型 | 格式 | 经 OpenCode Go 网关 |
|---|---|---|
| DeepSeek V4 | OpenAI Chat Completions 流式 | OpenAI 格式 (网关路由) |
| GLM (智谱) | OpenAI Chat Completions 流式 | 同左 |
| 千问 (Qwen3) | Anthropic Messages | Anthropic 格式 (网关路由) |
| MiniMax M2.x/M3 | Anthropic Messages | Anthropic 格式 (网关路由) |
| 月之暗面 (Kimi) | OpenAI Chat Completions 流式 | 同左 |
| ChatGPT (OpenAI) | Response API 流式 | - |
| Grok (xAI) | OpenAI Chat Completions 流式 | 同左 |

## Anthropic Messages (千问/MiniMax/ClaudeProvider 通道)
- max_tokens 必填; MiniMax M3 上限 524288 (推荐 131072), M2.x 上限 204800
  (推荐 65536); 超限或解释为上下文窗口 → 2013 (社区实锤 QwenPaw#1273,
  hermes-agent#37289: "does not support max tokens > 512000 (2013)")
- thinking: enabled/disabled/adaptive。MiniMax M3 官方示例用 adaptive;
  千问/阿里云兼容层: enabled/disabled + budget_tokens (废弃中, 改 effort);
  kimi-k2.7-code/k2-thinking/MiniMax-M2.5/M2.1 仅思考模式 (disabled 忽略)
- 约束: max_tokens 必须 > thinking.budget_tokens (qwen-code#2508: 相等 → 400)
- deepseek-v4 经 anthropic 兼容层: max_tokens = 回复+思维链总和
- system 顶层参数, messages 数组不接受 system 角色; user/assistant 交替
- tool_use 必须在 assistant 消息, tool_result 必须在 user 消息
- cache_control: system 尾块/消息尾块 {type:"ephemeral"}; 顶层 cache_control
  = 自动缓存模式; 最多 4 个断点
- MiniMax 1042 = 不可见字符比例超限 (BOM/控制符 → 客户端 BOM strip 防御正确)
- temperature 范围 [0,2) (千问) vs 官方 [0,1] — 兼容 0-2 无碍

## DeepSeek Chat Completions
- deepseek-v4-flash/pro: 上下文 1M, MAX OUTPUT 384K; thinking enabled/disabled
  (V4 默认开启思考) + reasoning_effort (low/high/max; medium/xhigh 映射 high;
  low 不支持直接报错 → 客户端映射 low/medium→high ✓ v3.6.49)
- max_tokens = content + reasoning_content 总和上限
- 多轮必须回传 reasoning_content (工具调用场景) — 客户端 includeHistoryReasoning ✓
- deepseek-chat 旧版: 4K 默认/8K beta; reasoner: 32K 默认/64K 上限
- 工具: tool_calls (id/type/function.name/arguments JSON 字符串)

## GLM (智谱)
- OpenAI 兼容; max_tokens 1-131072 (GLM-5 系列 128K 输出, GLM-4.5 96K)
- temperature [0,1]; extra_body thinking disabled/enabled 支持
- 经 OpenCode Go: 客户端不特判 (默认行为)

## Kimi (月之暗面)
- OpenAI 兼容; max_tokens 默认 1024 (长输出必须显式设置 8192+)
- K2.6: thinking_token_budget 顶层字段 (默认 8000) — 客户端不传用默认 ✓
- 风险: max_tokens 缺失时默认 1024 截断 → 客户端兜底 8192 (v3.11.7)

## Grok (xAI)
- OpenAI 兼容; max_tokens 默认 4096; grok-4 返回 reasoning_content
- 无 thinking 参数 (xAI 未支持) — 客户端对非 deepseek 模型不发 thinking ✓
- 建议长超时 (reasoning 模型) — readTimeout 3min 已覆盖

## ChatGPT (OpenAI Response API)
- ResponseAPI.kt (原版移植): max_output_tokens / input / context 结构
- 原版行为, 无自研改动 ✓

## 客户端关键校验结论 (v3.11.7 定稿)
1. ClaudeProvider max_tokens 兜底 64000: MiniMax M3 524288 / M2.x 204800 /
   千问 / DeepSeek anthropic 384K — 64000 全安全 ✓ (v3.11.6 已恢复)
2. thinking adaptive: MiniMax M3 官方示例支持 ✓; 千问兼容层忽略或接受
   (3.11.0 原版实测正常) ✓
3. ChatCompletionsAPI max_tokens 缺失兜底 8192 (Kimi 1024 截断防护) — v3.11.7
4. BOM/控制符 strip (v3.10.15): MiniMax 1042 不可见字符防护 ✓ 保留
5. 无签名 thinking 丢弃 (v3.10.12): 千问网关不自签, 回放 Minimax 400 根因 ✓ 保留
6. thinking disabled 仅对明确支持模型发送 (deepseek/moonshot/glm 等 host
   白名单) — Grok/未知网关不收 thinking 参数, 防 400 ✓ 现状已如此
