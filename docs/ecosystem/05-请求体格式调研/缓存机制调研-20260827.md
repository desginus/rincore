# 各家模型缓存机制调研 (2026-08-27)

## 结论总览
| 平台 | 机制 | 是否需要参数 | usage 字段 | 触发门槛 |
|---|---|---|---|---|
| DeepSeek | 自动硬盘缓存 (KV) | 不需要 | prompt_cache_hit_tokens / prompt_cache_miss_tokens | 无 |
| GLM (智谱) | 隐式自动缓存 | 不需要 | prompt_tokens_details.cached_tokens | 256 |
| Kimi (月之暗面) | 全自动 Context Caching | 不需要 | (usage cached) | 256 |
| 千问 (阿里百炼) | 隐式 (自动) + 显式 (cache_control) 双轨 | 显式可选 | cached_tokens | 256 (Qwen3.7 系~2000) |
| MiniMax | 显式 cache_control (Anthropic 兼容) | cache_control | cache_creation/read_input_tokens | - |
| Grok (xAI) | Anthropic 风格 cache_control / OpenAI 自动 | 自动为主 | - | - |
| OpenAI (ChatGPT) | 自动 prompt caching | 不需要 | input_tokens_details.cached_tokens | ~1024 (128 间隔断点) |
| Anthropic 官方 | cache_control 显式 (顶层自动模式/块级断点) | cache_control | cache_creation/read_input_tokens | 5min TTL |

## 各家细节

### DeepSeek (OpenAI 格式)
- 自动硬盘缓存, 对所有用户默认开启, 无需改代码
- 前缀单元制: 每条缓存前缀是独立完整单元, 后续请求必须完整匹配
- 落盘时机: 请求结束位置 / 公共前缀检测 / 固定 token 间隔
- 客户端对策: system 静态化 (缓存锚点 + stable/volatile 分区) ✓ 已实现
- 缓存"尽力而为", 不保证 100%; 自动清空 (几小时到几天)

### GLM (智谱)
- 隐式自动缓存, 无参数; 命中按更低单价计费
- usage.prompt_tokens_details.cached_tokens 透明展示 ✓ 客户端已解析

### Kimi (月之暗面)
- 全自动; >256 tokens 才缓存; 无需 cache ID/TTL
- 官方建议: 固定大段上下文放 messages 最前 (system 之前), 差异内容置尾
  → 客户端 system 消息在最前 ✓ 结构符合
- K3: max_completion_tokens 默认 131072 最大 1048576; 始终思考模式;
  reasoning_effort 顶层 (low/high/max 默认 max); temperature/top_p 固定值
  建议不传

### 千问 (阿里百炼, Anthropic 兼容层)
- 隐式缓存自动生效 (无法关闭, 命中 ~20% 计费), 触发 256 (qwen3.7 系 ~2000)
- 显式缓存: cache_control 断点 (system 数组形式), TTL 默认 5min,
  创建 ~125% 计费, 命中 ~10%; 两者可并存
- 客户端: ClaudeProvider 发 cache_control (system 尾块 + 消息级) ✓
  → 千问显式缓存命中率提升

### MiniMax (Anthropic 兼容层)
- 官方文档 "Explicit Prompt Caching (Anthropic API)": 支持 cache_control
  (type ephemeral, 可选 ttl 1h) — v3.11.6 恢复注入正确 ✓
- 兼容层 Supported Parameters 不含时被忽略 (3.11.0 实测正常)

### OpenAI (Response API / Chat Completions)
- 自动缓存: >1024 tokens, 128-token 间隔断点, 5min TTL 滑动刷新
- 无参数; usage.input_tokens_details.cached_tokens

### Anthropic 官方
- 显式 cache_control: 顶层自动模式 / 块级断点 (最多 4 个);
  TTL 5min/1h; 缓存键 = API key + 请求前缀

## 客户端缓存工程结论
1. ClaudeProvider cache_control 注入 (v3.11.6 恢复): 官方/千问/MiniMax 全支持
   → 恢复正确, 显式缓存全家族可用
2. OpenAI 家族全自动缓存: 客户端只保证前缀稳定 (system 静态化 + 工具顺序
   稳定 + 消息原样发送) ✓ 已实现
3. DeepSeek 前缀单元: 工具轮请求中工具结果在尾部 → 前缀不变 ✓
4. 已知不破坏缓存的自研机制: time_reminder 合并幂等 / 无签名 thinking 丢弃
   (thinking 内容每次不同, 丢弃后前缀稳定 — 缓存正向) / BOM strip
