## 三、I-11 四条「疑似实现回归」的核查结论

**核查方法**：不直接改断言（会制造假绿），逐条比对「测试期望」与「当前实现的真实语义」。

| 测试 | 期望 | 当前实现 | 判定 |
|---|---|---|---|
| `delete checks the version and removes the file` | 物理删除 | v5.3.19 起 `deleteFile` = **软删**（写 `invalidated_at`），物理删除走 `purgeFile` | **测试过期**。软删是有意为之（可恢复/可追溯），断言应改 |
| `invalidating a missing path reports false` | `false` | `invalidateFile` 走 `pathCandidates` **六形态匹配**；路径不存在时应返回 `rows > 0 == false` | **理论上应为 false，需实测**。若实测通过则纯属批量误标 |
| `changing scope of a truly missing path reports false` | `false` | `updateScope` 已返**真实行数**（v5.3.19） | **测试过期**（旧实现恒 true，断言写的是新行为但标了 @Ignore） |
| `MemoryFileTest > keys without an input field are kept` | `source: import` 保留 | `editableKeys = {name,title,description,aliases}`，`source` 不在其中 → **应保留** | **疑似批量误标**（v5.3.26 一次性标 31 条时未逐条核实） |

**为什么不改**：沙箱无 Android SDK、无 SnakeYAML 运行时 → 无法实跑验证。**在没有实测的前提下改断言 = 可能把真回归改成假绿**，比保留 @Ignore 更危险。已把上述判定写入 `KNOWN-ISSUES` 的 I-11 备注，下一轮有真机/CI 环境时按此逐条落地。

**同时发现一个结构性问题（记录在案）**：项目里存在**两个同名 `SkillFrontmatterParser`**（`data/files/` 与 `data/skills/`），`MemoryFile` 用的是 `data.skills` 那个（带 `compose`）。这是此前踩过的同名类坑（`SkillMetadata` 也是两份），`grep` 时必须看**完整包路径**。
