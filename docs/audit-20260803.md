# RinCore 系统梳理报告（石山审计）

> 日期：2026-08-03 | 版本：v3.5.1 | 触发：70K 冷启动注入未修复 + 技术债担忧

## 一、70K 冷启动注入（当前最严重）

### 根因（完整链路）
1. 工具池 264 tools（日志确认）——localTools + 搜索 + workspace + 生态 + 技能 + 域(3) + **MCP 动态工具**
2. `GenerationHandler` 分层模式（useLayeredTools 默认 true）按 loadedDomains 过滤——**但** `DynamicTools.getMcpTools()`（174 行）**绕过域机制全量注入 MCP 工具**（"mcp_connect 后立即可用"的设计）
3. **MCP 工具膨胀 = 70K 大头**：每个 MCP 工具 JSON（description + 参数 schema）~200-400 tokens；用户配置多个 MCP 服务器（搜索/工作流等）→ 200+ MCP 工具 → 60K+ tokens
4. **v3.5.1 修错位置**：只瘦身 system 内工具 systemPrompt（~870 chars→ 省几 K）——**tools 数组本身（60K）未动**——所以"无效"

### 为什么"当时修复了"
- v2.9.4 时代工具池小（几十个，无/少 MCP）——tools 数组 ~10K 无感
- "修复"的是 system 内重复注入（分层模式）——tools 数组本身随功能增减（MCP）膨胀——**这就是"功能增减带来的石山"**

### 修复方向（待实测确认后实施）
- **A（推荐）**：MCP 工具按域/按需加载——`getMcpTools()` 改为随 loadedDomains 注入（mcp_connect 工具本身保留在框架集；连接后工具归入服务器域，用户加载该域才注入）——预计 264 → 50-80 tools
- **B（保守）**：MCP 工具 description 截断（收益有限——schema 才是大头）
- **C（配置）**：确认 assistant.useLayeredTools 是否被用户改为 false（false=全量兜底→直接 70K）
- **诊断已加**：toolsInternal (layered/full) 日志输出 total/mcp/framework/domain 构成——下次运行可精确定位

## 二、回滚缝隙（3.2.2 传输层 + v3.4.x 业务代码）

### G1. BEFORE_SYSTEM_PROMPT 协议违规潜伏（P0 风险）
- 3.2.2 的 PromptInjectionTransformer = v2.9.5 独立消息版（user 消息插 system 前）
- **DeepSeek V4 Flash 严格端点**要求首条为 system → 注入触发时报 SETTINGS（B11 根因就在 3.2.2 基线里）
- **建议**：低风险移植 v3.4.5 的合并修复（BEFORE_SYSTEM_PROMPT → 合并进 system 开头）——与既有测试期望一致

### G2. 孤儿 tool_call 无清洗（P1 风险）
- 3.2.2 无 sanitizeToolCallSequence（v3.3.13 才引入）——流中断/工具失败产生的孤儿 tool_call 残留 → 平台消息序列校验风险
- **建议**：评估重移植 v3.3.13 的清洗（循环内每步 + 移除所有未配对）

### G3. 空流无应对（P1 风险）
- 平台偶发空流（19 秒静默 [DONE]）无重试、无诊断（v3.4.7 补丁已移除）
- **建议**：观察——若 3.2.2 基线请求结构下空流不再出现（可能是 v3.4.x 请求结构触发）则无需处理；若再现，重移植空流重试

### G4. 缓存断层诊断缺失（P2）
- v3.4.1 的 cache: prompt/cached 日志 + 缓存断层! 检测已随回滚移除——下次 9.7K 无法定位平台 vs 客户端
- **建议**：重加（低风险、高诊断价值）

## 三、其他石山（功能增减积累）

### S1. 工具池无启用过滤（P1）
- 264 工具全量注册——未按域启用状态过滤 tools 数组（域分类只影响 system 层1概览）
- 与 G1 修复联动（MCP 按需加载）

### S2. DB migration 早期链缺失（P2 低风险）
- version=27，但 migration 文件仅 11 个（6_7, 8_9, 14_15...25_27）——7_8/9_10 等早期缺失
- 运行正常（用户在用）——推测早期用 fallback 或合并——**不建议动**（无证据表明有问题）

### S3. 测试覆盖有限（P2）
- 27 个测试（transformer/ResponseAPI 序列化为主）——**传输核心链路（GenerationHandler 工具池构建/域过滤/清洗）无测试**
- 建议：G1/G2 修复时补对应测试（PromptInjection 已有测试可复用）

### S4. 注释与实现脱节（P3）
- buildCacheAnchor 注释"静态规则块 + 工具目录 ~870 chars"——实际纯静态规则块（无工具目录）——误导排查
- 建议：修正注释

### S5. runBlocking 使用（P3 可接受）
- AlarmTools（AI 工具执行环境——允许）+ WorkspaceDocumentsProvider（ContentProvider 必须同步）——低风险

## 四、修复优先级

|:---:|---|---|---|

## 五、结论
- **70K 不是回滚引入**（v3.4.x 也有 264 工具）——是 MCP 功能增减积累；回滚暴露了它（用户实测冷启动）
- **回滚缝隙 4 处**（G1-G4）——G1 是 DeepSeek 场景下的真实隐患（SETTINGS 根因在 3.2.2 基线内）
- **修复原则**：只移植验证过的补丁（G1= v3.4.5 已验证；G2= v3.3.13 已验证）——不整体照搬
