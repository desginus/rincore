# RinCore 开发流程（Scrum 式工作流）

> 本流程由多次血泪教训固化——**违反任一条都会挨骂**。逐条执行。

## 0. 总则（血的教训——违反即错）

1. **版本号第三位每次发版必须递增**（4.0.5 → 4.0.6）——用户靠版本号判断是否新构建。versionCode 锁 9999 只动 versionName（release 按 versionName 打 tag）。版本号与代码修改**同一次提交**，漏改会导致 release 落进旧 tag（v4.0.6 教训）。
2. **改完必须本地验证 → 展示给用户确认 → 才推送**。绝不"改完直接推"（用户骂过两次）。
3. **推包 = build.yml artifact 直链**。绝不搞 daily-build / Prerelease / 其他花活（用户明确不要）。
4. **"推送"≠"交付"**：用户拿到新 APK（版本号可见）才算交付。推送后必须给 artifact 下载链接。
5. **没有证据不猜**：协议/格式类问题没有实际日志（logcat 事件结构）时，先加诊断日志定位，不盲改。

## 1. 问题分析流程

```
1. 定位触发点    — 日志/报错位置（CallTracer 事件 / logcat / 用户描述）
2. 全代码过一遍  — 搜索所有相关引用：同函数 / 同链路 / 同模块（grep 全量）
3. 爬所有相关    — 调用链上下游 + 历史记录对照（rincore-bug-record 先查：
                   是否已修复过 / 是否回滚丢失 / 根因是什么）
4. 根因确认      — 找到"为什么"（不是"看起来像什么"）
                   - 对比 fork / upstream / 历史提交（git log 回溯关键点）
                   - 无证据时：加诊断日志（Log.i — release 可见）让用户跑一次
```

**诊断日志标准**：关键链路日志用 `Log.i`（release 构建也打印）——`Log.d` 在 release 被过滤，用户看不到。

## 2. 修改纪律

```
1. 小步改    — 一次一个点，改完立刻验证（不做大杂烩提交）
2. 不破坏其他 — 改 A 必须检查同模块/同链路的 B/C/D（引用处全查）
3. 结构优先  — 能架构化不特判（如 capabilities 字段 vs 内联 if(host)）
4. 参考成熟实现 — fork / upstream / 历史提交先查（可能有现成答案）
5. 测试同步  — 新逻辑必须有单元测试（反射调 private 也行）
```

## 3. 梳理流程（改完之后）

```
1. 语法检查    — 修改文件括号/字符串平衡（python 脚本，注意字符串字面量）
2. 内容确认    — grep 修改点，确认改的是预期位置、无残留（如变量名遗留）
3. 影响面梳理  — 修改点引用的上下游再查一遍（签名变更 → 调用处/测试全查）
4. 与既有测试期望对照 — 改行为前先看测试怎么期望（v2.9.5 偏离测试的教训）
```

## 4. 测试流程

```
1. 单元测试：新增逻辑补用例（协议序列化用反射调 private 方法）
2. 本地跑不了（无 Android SDK）→ 靠 CI 验证（推送后 build.yml 自动跑）
3. CI 绿 = 编译 + 测试通过 — 红则拉日志修（不重复推）
```

## 5. 推送流程（用户确认的唯一方式）

```
1. 本地提交（commit）— 先给用户过目（改动内容 + 影响说明）
2. 用户确认 → push origin main --no-verify
3. build.yml 自动构建（约 10-15 分钟）— CI 绿 = 构建成功
4. 给用户 artifact 直链：
   https://github.com/desginus/rincore/actions/runs/<run_id>/artifacts/<artifact_id>
   （rincore-release 包，35MB，7 天保留，GitHub 登录下载）
5. 提醒用户确认版本号（设置页显示 3.5.x）再测
```

**绝对禁止**：
- ❌ 直接 push 不给链接（用户拿不到新包 = 白推）
- ❌ daily-build / Prerelease / 手动 Release（多余花活）
- ❌ 版本号不动就推（用户分不清新旧包）
- ❌ 改完不验证直接推

## 6. 沟通纪律

```
1. 每步汇报：分析结论 → 改动内容 → 验证结果 → 推送状态
2. 批评立即认：流程错了先承认再补救（不辩解）
3. 不猜用户意图：拿不准就问（推送时机/版本号/回滚范围）
4. 诚实：没证据不装懂（"需要日志"就说需要日志）
```

## 7. 常规操作速查

| 操作 | 怎么做 |
|---|---|
| 修 bug | 流程 1→2→3→4→5（分析→改→梳理→测试→推） |
| 升版本 | 第三位 +1 + versionCode +1（与代码同提交） |
| 查历史 | rincore-bug-record（根因/是否修过）+ git log 回溯 |
| 拿 APK | build.yml artifact 直链（run 页） |
| CI 状态 | scripts/ci-check.sh 轮询 |
| 诊断问题 | 先加 Log.i 日志 → 用户跑一次 → 证据到手再改 |
