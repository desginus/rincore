# RinCore Bug 记录（全部历史）

## B193 图片"渲染出错误的图"两层机制 + 渲染即固化根治（v4.8.185）
- **现象（用户）**：模型经常渲染出错误的图片——一批图里个别张是错的；要求"整个重新过一遍，有问题的直接重写"。
- **根因（A+B，均为结构级）**：A) 消息存的是**地址活引用**——显示时实时"地址→文件→解码"，同名路径被后续覆盖时**所有历史消息被回灌成新图**（Coil mtime+size 键保证覆盖后必重解码）；B) `WorkspaceImageResolver` 归一化 host 地址时**丢弃工作区 UUID**（注释原话"UUID 段忽略"）+ 全库 first-hit——多工作区同名文件命中错工作区。B155/B158 命名链复核无恙（非本案来源）；附属缺陷=尺寸预读链与 Coil 认领层不同源。
- **修复（重写非补丁）**：①生成完成固化器（ChatMediaStore 快照 + 地址重写，幂等、自动回填历史）；②resolver UUID 定点优先；③解析函数单一化（utils/LocalImageAddress）；④导出 data URI 携图；⑤删除清理。
- **教训（#114-116）**：①"引用型媒体"必须区分**活引用**与**固化快照**——观感/正确性问题常源于渲染时机的活解析；②地址里的标识段（UUID）被"为了容错"丢弃=确定性错配温床——"地址说什么就解析什么"是收敛方向；③同域解析能力必须单一来源（三处解析链能力不一致=谁都说自己没 bug）。

## B192 标题栏"板带+分界线"（v4.8.183 → v4.8.184 修复）
- **现象**：用户截图实证——标题栏呈一条比背景亮、带灰颗粒的"板带"，下沿一条硬分界线（"根本看不了"）。
- **根因**：183 标题栏模糊用 Material3 预设（inputBlurStyle/inputTopStyle）：①预设自带不透明底料（surfaceContainerLow 实底；标题栏侧无蒙版/雾调和→显成"板"）②S1 噪点映射 0.6 铺灰颗粒；硬线=裁剪边缘。
- **修复**：RinGlass.titleBlurStyle（透明底+零噪点）+ 顶栏单层纯模糊：空背景无痕、正文滑入被磨掉。

## B191 — 渲染终局归因：为什么 4.8.176（=119 栈）"好多了"（v4.8.177 归档）
- **决定变量=模糊半径（物理像素）**。它同时控制两条"放大链"的开合：
  ① haze `BlurInputScalePolicy` 分档（源码已核实）：物理半径 ≥32px→模糊输入 0.8 档、≥60px→0.5 档，算完非整数放大回放=规则采样网格；
  ② GPU/Skia 大半径模糊内部多级降采样再放大（推断，170 截图"10px 锐利方块"物证）。
- **换算表（屏幕密度≈2.7-3）**：4dp≈10-12px=两链全关（干净）；12dp≈32-36px=0.8 档开启；24dp≈65-72px=0.5 档开启。与用户实测"4 细/12 明显/24 重"完全一致。
- **环境层**：haze 2.0.0-beta01 + Compose BOM 2026.08.00（=119 逐字环境）随 176 归零，消除 167/168 引入的历史变量。
- **判据（用户语言与物理解释的统一）**："细到看不出规则周期=磨砂玻璃（真磨砂=无序细颗粒）；可见规则周期=管线伪影"。格栅非"消除"而是细至不可辨。
- **推论（供后续）**：任何"加大半径的重磨砂"在同设备上会机制性重开两链——不要再向大半径方向求解。

## B186 — 输入框「织物/条纹」纹理 = haze 自适应保真降采样档（v4.8.169）
- **现象**：165-168 五版（4dp/12dp × beta01/2.0.0 × BOM 新旧）输入栏模糊均呈「一条一条交错织物/条纹/格栅」；用户同屏对比原版 2.5.6「就是对的」，并给出判据：「把格栅和条纹弄得特别特别细，够细=磨砂玻璃」。
- **取证（代码面归零）**：玻璃链全部变量与原版逐字对齐（haze 2.0.0、Material3{blurRadius(12.dp)}、源注册 3 处、composer 链、Compose BOM 2026.09.00）后仍复现 → 差异不在「配了什么」，在**运行时保真度决策**。
- **根因（机制，源码级）**：`BlurInputScalePolicy`（haze 2.0.0）按 `radius≥32px && area≥300k×multiplier(1→3)` 把模糊**输入**降采样到 0.8（更狠 0.5），绘制时非整数放大回放——输入栏 12dp 在密度≥2.67 恒满足半径条件、面积在阈值边缘且滚动期 multiplier×3 必过线 → 纹理粒度随「滚动/静止/背景动画」波动，颗粒=采样网格。
- **修复**：输入框族 hazeBlur 传 `performanceMode = HazePerformanceMode.Quality`（=Fixed(1f)→恒 1.0 全分辨率，脱离 cadence/滞回）；全屏编辑器同规格。弹窗/轨道图标小面积恒 1.0 档不钉。
- **教训（#96）**：观感纹理粒度类「玄学」反馈，先读渲染库的**保真度/分档策略源码**再对参数——自适应策略是「参数全对仍不对」的隐形变量；显式钉死档位（HazePerformanceMode）是治「随机纹理」的正解。
- **待真机验证**：输入栏模糊 = 均匀全分辨率磨砂（滚动时不再出现织物/条纹颗粒）。若仍不符 → 需要同条件双截图（原版/我们，同助手同背景同滚动位置）作为唯一权威数据，不再脱离像素改码。

## B185 — 输入框「织物感/色块」终局：渲染器版本落后（v4.8.168）

## B182 — "输入框没有做高斯模糊"（十轮玻璃争论的总根因，v4.8.157）
- **现象**：用户历轮反馈"隔山/隔栅/黑/不透明/散光/没做高斯模糊"——玻璃链看起来从未生效。
- **根因（实锤）**：存量 `displaySetting.enableBlurEffect` **恒为 false**（从未开启）→ 输入框/弹窗/轨道图标全部走**回退板块**路径（半透明填充，无 haze 真模糊）。v4.8.146-156 所有玻璃参数调整（4/8/20dp、噪点、tint、alpha、frostFill…）对用户**全部不可见**——争论的"玻璃"一直是回退板块。
- **修复**：一次性强制开启迁移（`blurEffectUpgraded` 标记，镜像 v4.8.139 模式）；升级后恢复用户控制。
- **教训（#84）**："效果不存在"类反馈第一步 = 查开关值及其持久化真值；用户描述的"效果"可能根本不是你以为的那条渲染路径。

## B183 — 对话切换"闪一下、卡一下"（v4.8.157）
- **现象**：抽屉切换不同对话，生硬、偶发闪/卡；"系统根本来不及反应"。
- **根因**：抽屉切对话 = `navigateToChatPage` → `clearAndNavigate` **清栈直切**——旧内容瞬间消失、新页面首次重组合（重活）全部暴露在屏幕上。
- **修复**：`Screen.Chat` 元数据转场 = **fade-through**：140ms 淡出 → 背景停顿窗（吸收重组合卡顿）→ 延迟 200ms 起 260ms settle 淡入（用户自述"做一个过渡掩盖掉就很简单"的实现）。
- **教训（#85）**：清栈式导航切换无遮挡 → 用"淡出→停顿→淡入"掩盖；停顿窗 = 重组合卡顿的专用吸收窗。


## B181 — "整页蒙黑纱 / 背景串了"（v4.8.146-154 玻璃链整块回滚定案，v4.8.155）
- **现象**（用户）: ①"整个页面被蒙了一层黑纱"；②"现在所有助手的背景彻底串了"。
- **根因（结构级）**: v4.8.146 起在对话区加了一层**覆盖整页的玻璃背衬面板**——任何整页玻璃 = 天然"蒙层"；其模糊输出依赖对背景层的**捕获/缓存**，页面又从未有过如此大面积的玻璃消费面，捕获陈旧/错位时整页呈现"错误背景"（感知为背景串）。
- **处置（用户指令"彻底回滚"）**: 玻璃链 146-154 整体撤销回 v4.8.145 状态（面板移除 + RinGlass 整档还原 + 填充/默认值还原）；非玻璃交付（轨道/胶囊/标题/切换修复等）在回滚基线上保留。
- **教训（#81）**: 大面积（接近整页）玻璃层 = 高风险设计——"蒙层感"与"捕获错位"两类问题皆源于此；整页级观感问题优先回滚结构，而不是在玻璃参数上继续摆动（在 147-154 摆动 8 轮未愈）。


## B179 — 输入框"黑的、压根不透明"（v4.8.153→154 机制级根修）
- **现象**（用户）: v4.8.153 后输入框"是黑的，压根不透明"（0.65 填充本应 35% 透出）。
- **根因（机制级）**: 模糊图层合成 alpha=1——背景（动态渐变 Mesh/壁纸，全幅不透明）→ blur(不透明)=不透明 → 填充浓度调整无效（透出的是模糊层，不是底下内容）。
- **修复**: `HazeBlurStyle.alpha(0.4f)`（模糊图层 40% 合成；haze 源码取证 layer.alpha=blurVisualEffect.alpha）+ 双路径防御（开关默认 true / 回退底色 0.65）+ 填充保持 0.30 → 底下内容实际透出约 42%。
- **教训（#80）**: "半透明"三要素逐一核销：背景源（只含大色块背景）+ 合成透明度（style.alpha）+ 填充浓度；数学上透出量 = (1-图层alpha)×(1-填充alpha)。


## B178 — "散光/又黑又隔栅"：模糊源含消息列表 + tint 滤镜（v4.8.153）
- **现象**（用户，警告一次）: 消息区的复制/转发按钮与消息本体出现"散光感"；输入框"又黑又有隔栅感"。
- **根因**: ① 消息列表（LazyColumn）被注册为 haze 模糊源 → 面板/输入框模糊输入 = 背景+消息 → 面板背景是"模糊后的消息"，清晰内容画其上 → 每个形状周围渗出模糊虚影 = 散光；② colorEffects 材质 tint（surface@0.5）在深色主题把玻璃压成黑板（"黑"）；输入框内文字拖影（"隔栅"）。
- **修复**: 消息列表退出模糊源（只模糊背景） + 撤 tint + `frostFill()`（0.65 半透明填充）= "半透明+高斯模糊"最简玻璃。
- **教训（#79）**: 模糊源只允许"大色块背景"；内容层（文字/图标）入源=自带虚影；用户基线审美="半透明+高斯模糊"，花哨 tint/噪点为偏离项。

## B173 — "柔光玻璃"三个版本的观感失败（v4.8.146→150 定案）
- **现象序列**（用户逐版反馈）: v4.8.146"很强的隔山感"；v4.8.147"极差，隔栅感极重"；v4.8.148"还是很糟糕"。

- **教训（#76）**: 玻璃三件套=深模糊+零噪点+材质 tint；"柔光"的本质是 tint 不是 blur；噪声在"质量"层面永远劣化观感（颗粒），抗色带应由 tint 层承担。

## B138 — 「发送后一直加载、首次输出不出现」实为系统按应用联网封锁（v4.8.114 加固可见性；非代码回归，不回滚）

### B122. STDIO MCP 全部连不上（v4.8.96，fork SDK 探测 + stderr FATAL 双重放大器）
- **现象**：v4.8.94（MCP SDK 切 rikkahub fork）后，所有 stdio 格式 MCP 工具"连不上"；HTTP/SSE 不受影响。
- **根因链（本地复现实锤）**：fork SDK 客户端默认 `ProtocolEra.Auto`，连接时先发 `server/discover` 探测 → 老服务器不认识该方法，通常把 "unknown method" 记到 **stderr**（含 "error" 字样）→ 沿用 SDK 文档示例的 stderr 分类器把含 "error" 行判 **FATAL** → 传输层 `stopProcessing` 停机 → connect 抛 `McpException: Connection closed` → 重连链反复同样失败。
- **复现**（kotlinc 2.4.10 + fork jar 直跑 fake stdio server）：Auto+stderr日志 = FAIL(699ms)；Legacy = OK(306ms)；慢启动(8s)/静默服务器在 Auto 下均能优雅回退（排除"只是慢"的猜测）。
- **修复**：① `createSdkClient` 强制 `ProtocolEra.Legacy`（恢复官方 0.15.0 的 initialize 握手，不发探测）；② stderr 分类器**永不 FATAL**（error→WARNING；进程真死由 EOF/onClose 正常处理）。
- **教训**：SDK 大版本/换源升级，连接级行为必须**本地复现验证**（复现法：kotlinc + 依赖 jar 直跑 SDK，成本约 20 分钟，远低于盲推 CI）；"上游默认值"在**上游无该功能面**时没有参考性（stdio 为自研 viaWorkspace 桥，上游无 stdio）；stderr 关键词分类天然危险，FATAL 慎用。

### B120. shell 输出截断丢掉编译报错（v4.8.82 头+尾双保留）
- **现象（自证）**：跑编译/构建类命令时，明明构建失败，工具结果里却看不到任何报错，只在一个孤零零的 `"truncated": true` 旁边结束。模型据此下"命令没报错/构建正常"的错误结论。
- **根因**：`workspace/.../WorkspaceShellRunner.kt` 的 `StreamCollector` 只保留**前** `MAX_OUTPUT_CHARS`(=128K) 字符，超出部分**直接丢弃**（`if (read > remaining) truncated = true`，后续数据不再入缓存）。而编译器/构建器的输出形态是"开头一片下载/守护进程进度噪声，**错误与总结在尾部**"（Gradle `> Task … FAILED` / `e: file://… Unresolved reference` / `BUILD FAILED`、CMake、pip、npm 皆然）。日志一旦超过 128K，最有价值的尾部整段消失 —— **截断方向与信息价值方向正好相反**。
- **修复（v4.8.82）**：`StreamCollector` 重写为**头+尾双保留** —— 前 48K 进 `head`，其后按环形缓冲保留**末** 76K；中段丢弃但记录省略量，`text()` 在省略处插入显式标记 `... [已省略中间 N 字符] ...`（头+尾+标记 ≤ `MAX_OUTPUT_CHARS`）。省略量经新增的 `WorkspaceCommandResult.omittedChars` 上报；`workspace_shell` 结果新增 `omittedChars` / `note`（超限，附"重定向到文件再分页读"的处置）与 `hint`（超时 = 中途截断残段 → 引导 `workspace_job`）。未超限时逐字不变（先喂满 head 再进环形缓冲）。
- **顺带**：`workspace_grep` / `workspace_glob` 的 `truncated = lines.size >= maxResults` 属误报 —— `head -n N` 拿到的是**截断后**的结果，"恰好 N 条"与"不止 N 条"无法区分，模型会为此反复换 pattern 重搜。改为取 N+1 行再判定（`lines.size > maxResults`，多出的那行丢弃）。
- **验证路径**：`/workspace/scripts/verify-truncation.sh`（拉与项目同版本的 kotlinc 2.4.10 真编译整个 workspace 模块 + 真跑）。编译通过；真实进程边界矩阵 n=0/1/100/49151/49152/49153/126975/126976/126977/300000/1000000 全 PASS；4000 行构建日志场景中三行报错均落在保留尾部（旧实现下三行全丢）。
- **教训**：**截断方向必须对齐信息价值方向** —— 日志类有价值的是尾部（结论/报错），文件类有价值的是头部；只截一头必然有一类场景失真。且截断必须把"我截断了、截了多少"显式告诉消费方：**静默截断比不截断更危险**（会让模型把"看不到"当成"不存在"）。

### B54. "usage 尾包启发式"掩盖掐断 — 静默截断二次根治（v4.8.56, B53 姊妹篇）
- **现象（用户实证, 4.8.55 后）**：GLM-5.3-flash 输出仍"瞬间中断"、无报错、自动续写不触发；两轮 trace 的最后关闭均走"正常完成"分支（gotFinish/completed=true，即完成标记被提前置位）
- **根因实锤**：v3.6.78 的"usage/cost 收尾行即完成"启发式无 opencode 门控 — opencode 网关的"上游死亡前的最后 usage 报告"与"正常完结的收尾 usage 行"形态完全相同，掐断被静默判为正常完成（v4.5.12 注释即实证过该形态；其心跳否决只覆盖"usage 后仍有内容"场景 — 掐断紧随 usage 时仍被掩盖）
- **修复（v4.8.56）**：① opencode 撤销该启发式（交 onClosed 详细判据；非 opencode 零变化）；② 掐断疑点判定"usage/cost 纯尾包 + 尾部无收尾标点即关流"（grok 豁免 — 其正常完结即 usage 尾包形态）→ 命中即合成 Finish(length)；③ 截断关闭升级为自动续写（无缝续进同一条消息，上限 3 次）；④ 完成明细入 trace（completed/finishReason/hasText/tail — 用户导出日志即可定性）
- **教训**：① 启发式完成标记是"静默截断"的最大温床 — 任何"近似完成"信号都必须可被详细判据复核；② 网关生态的"正常完结"与"上游死亡"形态重合时，宁可多判"疑似截断"（自动续写有界）也不可静默放行；③ 完成信号来源必须进 trace

### B53. GLM-5.3-flash 输出"异常中断无报错" — 长度截断静默收尾（v4.8.55 根治）
- **现象（用户实证）**：OpenCode GLM-5.3-flash 输出异常中断、无任何报错（346s 长生成后对话直接结束）
- **追踪**：最后一次关闭走"正常完成"分支（gotFinish/completed=true，即流内收到过完成信号）→ 高度吻合 finish_reason=length（输出预算打满；GLM-5.3-Flash 最大输出 128K，达到上限时流自动停止返回已生成部分 — zai-org 官方文档；OpenCode 生态 GLM 长会话流截断为已知问题 zai-org/GLM-5 #66）
- **根因**：客户端对"纯正文被 length 截断"零处理 — 工具调用截断有 v4.5.2 修复链，纯文本截断则无续写、无提示，静默收尾（仅日志留痕）
- **修复（v4.8.55）**：自动续写机制 — finish_reason=length + 末条纯文本（无待执行工具）→ 下一轮请求级注入续写引导（不落盘不显示），流式内容直接续写进同一条 assistant 消息（无新气泡无引导气泡）；工具全截断场景同样自动续写；相邻 Text 分片自动合并；上限 3 次；耗尽仍截断 → 明确报错（杜绝静默截断）
- **教训**：① finish_reason 的每一种取值都必须有客户端语义分支（length ≠ "正常完成"）；② "用户无感知"的自动续写是 agent 应用处理输出上限的正确形态（显示报错=打断体验；静默截断=信任损伤）；③ 跨函数状态用 per-generation 对象模式（与 RetryState 同款，并发安全）

### B52. 聚合网关上游瞬时错误 — CC 通道无分流直接终态（v4.8.39 首发 / v4.8.54 扩展）
- **现象（用户实证）**：CC 通道生成失败: HttpException "Upstream request failed: Invalid request parameters. Please check your input and try again."（栈: ChatCompletionsAPI onFailure → parseErrorDetail）
- **根因**：该错误为 OpenCode 网关对上游调用的失败包装（社区实证网关侧瞬时问题、重试可恢复）；v4.8.39 仅对 ResponseAPI+grok 场景做了分流，CC 通道无此分流且 4xx 被设计为终态不重试 → 直接弹错
- **修复**：CC onFailure 补场景分流 — 仅聚合网关（opencode.ai / api.commandcode.ai）且消息属瞬时家族（"Upstream request failed" / "Upstream response was not valid JSON" / "Endpoint is unavailable"）时包装 IOException → 上层重试链
- **教训**：网关/上游的"瞬时错误家族"要按**通道 × 网关矩阵**核对覆盖（一个通道修了 ≠ 全通道覆盖）；若同一错误在固定对话/模型"必现"→ 另查请求体（运行日志 onFailure 行含 http/REQ/RESP 摘要）

### B51. 图片保存"提示成功但相册没有"假成功（v4.8.53 修复）
- **现象（用户实证）**：图片预览 → 下载 → 提示保存成功，相册中不存在该图片
- **根因链**：① saveMessageImage 各分支存在静默失败路径（workspace resolve 返回 null / http 解码 null / 源文件不存在 / exportImage 内部 catch 全吞异常）；② 调用方（ImagePreviewDialog / ImgGenPage / Mermaid）无条件提示"已保存/导出成功"；③ Q+ MediaStore 写入未用 IS_PENDING 两段式（部分 ROM 下未 finalize 条目不被图库收录）；④ exportImageFile 一律命名 .png/image/png，与 JPEG/WebP 实况不符
- **修复（v4.8.53）**：MediaStore 两段式（IS_PENDING 1 → 写入 → 置 0，失败删除占位行）+ 按源扩展名推导名称/MIME + 全链 Boolean 真实结果 + 四个调用点按结果显示成功/失败 + Log.i/Log.w 全链留痕（运行日志可查）
- **教训**：**用户提示必须由真实结果驱动**——"吞异常 + 无条件成功提示"= 假成功，是用户信任的致命伤；媒体库写入两段式是各 ROM 通吃的标准写法

### B50. 压缩蓝标误触（v4.8.51 修复）

### B49. 缓存命中率三坑（v4.8.51 修复）
- **现象**：缓存上线后命中率存疑（反复核验）
- **三坑**：① **键不匹配（零命中根因）**：渲染前对正文做 replaceRegexes(visual=true) 变换，而预热写的是原始文本——两条键根本对不上；② **流式污染**：每条流式中间态（每几十毫秒一个新全文）都在写 LRU，把稳定内容全挤出去；③ **分支裸奔**：MarkdownNew（HTML 消息）的 HTML 生成与 Jsoup 解析无缓存，每次重进组合全量重算
- **修复**：①预热同步执行同一 replaceRegexes 变换（键一致）；②变化路径改 parseTransient（只读不写）；③MarkdownHtmlMemo 记忆化（首帧可写、变化只读、doc 限 32 条/≤200K html）
- **教训**：缓存三要素——**键一致性（预热≡渲染）/ 污染控制（中间态不写回）/ 覆盖全面（全部分支）**；命中率为零先查键，再查污染

### B28. 多模型异常中断 — 无完成信号关流被误判"正常完成"（v4.5.20 修复）

- **根因**：ChatCompletionsAPI 的 grok 通道完成启发"收到 usage/cost chunk 即 gotFinish=true"**无条件置位**（原为 grok 不发标准结束信号而设）；OpenCode 网关对长思考流中途发 usage 心跳 → 完成标记提前武装 → 服务器随后断流 → 关流检查见标记就把半截思考当正常完成静默接受。fp_drift 实证：同会话轮间 ntools 47↔21 波动，toolsHash 变化致前缀缓存全灭（命中率 5%）
- **修复**（四层）：①带实质 content/reasoning delta 的 chunk 不置位；②置位后任何实 delta 到达即撤销（"流还在产出就不算完成"；grok 式 usage 结尾流不受影响）；③finish_reason=length 显式 Log.w（截断可见化）；④流结束归因日志（completed/gotFinish/finishReason/events/model）——中断现场日志可直接确证
- **同批**：顶层工具集恒定（用户判满定性）——顶层=FRAMEWORK_TOOL_SET+exemptSet+memory_tool/invoke_tools，域内工具严禁进顶层，一律 invoke_tools 动态执行（全量池 classifyAll，不依赖顶层定义）
- **教训**：**"X 信号即 Y 状态"必须问 X 是否必然蕴含 Y**——usage 在流尾才是完成、中途是心跳（置位必须可撤销）；完成标记必须记录 finishSource，中断才能归因。**请求体动态集合必须会话内恒定**——tools 在 messages 之前，toolsHash 变化=前缀缓存全灭，"追加尾部"只防增不防减

### B17. 冷启动注入 70K tokens（v3.5.1 修复）
- **现象**：回滚 3.2.2 后每次对话起始冷启动注入 70K+ tokens

- **修复**：else 分支移植 v2.9.4 瘦身逻辑——只注入 7 个框架工具（invoke_tools/workspace_*/manage_domain/list_domains/move_tool_to_domain），其余工具描述在请求 tools 数组
- **验证**：system 从 ~70K → ~10K tokens

### B16. Responses API reasoning 回传格式（v3.4.9-3.4.10）
- **现象**：DeepSeek（Responses API + thinking 模式）工具调用后中断——"The reasoning_text in the thinking mode must be passed back to the API"
- **根因**：ResponseAPI 回传历史 reasoning 用 OpenAI 标准独立 reasoning item（summary_text）——DeepSeek 要求 summary 元素类型为 reasoning_text
- **坑**：v3.4.9 曾在 content 数组加 reasoning_text 块 → 被拒 "unknown variant reasoning_text, expected input_text/output_text/input_image/input_file"（content item 类型枚举不含 reasoning_text）——正确位置是独立 reasoning item 的 summary 数组
- **修复**：summary 元素类型按 host：deepseek → reasoning_text；其他 → summary_text
- **触发链路**：启动正常（无历史）→ 思考正常（单请求内）→ 工具调用后请求携带思考轮次历史 → 回传格式错 → 中断
- **注意**：v3.5.0 已回滚传输层——此修复已移除；若 3.5.x 再遇此错误需重新移植（位置：ResponseAPI.addAssistantItems 的 summary 数组）

### B15. ChatCompletions DeepSeek reasoning 回传（v3.4.8）
- **现象**：DeepSeek 思考模式报 "reason text 必须返回给 API"
- **根因**：includeHistoryReasoning 受 provider UI 开关控制，关闭时剥离历史 reasoning
- **修复**：host.contains("deepseek") 强制 includeHistoryReasoning=true
- **审计结论**：客户端全链路（appendChunk/sanitize/buildAssistantMessageJson/DB 序列化 @SerialName("reasoning")）均保留 reasoning——唯一漏洞是开关

### B14. 千问前几轮缓存率低（v3.4.8 确认非 bug）
- **现象**：9K 测试文本无缓存、前几轮缓存率低

### B13. DeepSeek V4 Flash 输出中断（v3.4.7 补丁——已随回滚移除）
- **现象**：流式中途中断，无错误；日志 SEND → RECV messages=8（无新增）——模型 19 秒返回但流无有效 chunk（平台偶发空流）

- **注意**：v3.5.0 回滚后此补丁已移除——3.5.x 再遇中断需从 3.2.2 基线重新诊断（先看是否仍是平台空流，再决定是否重移植）

### B12. 生成中切后台回答全部消失（v3.4.6——回滚后保留）
- **现象**：模型运行中切后台，重新进入后回答全部消失（灵动岛还在显示输出但对话页丢失）
- **根因**：assistant 消息仅在生成结束（onSuccess）落盘；生成中只有内存 flow 更新；user 消息发送时已落盘（所以只丢回答）
- **修复**：GenerationChunk.Messages 分支每步 saveConversation（流式增量落盘）+ onCompletion 兜底落盘（异常/中断路径）

### B11. Required SETTINGS preface not received（v3.4.5 根治——已随回滚移除）
- **现象**：DeepSeek V4 Flash 流式中断，报 "Required SETTINGS preface not received"；古早版本无此问题
- **根因**：v2.9.5（缓存锚点+注入隔离）把 BEFORE_SYSTEM_PROMPT 注入改为独立 user 消息插到 system 前 → 首条非 system → 严格端点拒绝
- **偶发性**：注入为触发式（lorebook 按上下文触发），搜索工具结果加入后重新 transform → 注入出现 → 首条变 user
- **修复**：BEFORE_SYSTEM_PROMPT 合并进 system 开头（无 system 时创建 system 消息）+ GenerationHandler 协议兜底（首条非 system 自动合并）
- **教训**：v2.9.5 的实现偏离了既有测试期望（测试至今仍期望合并语义）——改代码先看测试

### B10. 定时任务崩溃 FGS type=none（v3.4.4——回滚后保留）

### B8. 权限管理点击无反应（v3.4.2）
- **现象**：权限管理页点击不跳转/无反应

### B7. DeepSeek 缓存阶段性断层（确认非 bug）
- **现象**：token 稳定上增、缓存阶段性跳台阶（60K 附近常断，断后 ~9.7K 公共前缀）
- **根因**：DeepSeek 前缀单元制——每个缓存前缀是独立完整单元，后续请求必须完全匹配；60K 附近跨固定间隔单元边界 → 单元结构重排；模型输出/工具结果长度波动导致请求边界单元切分点移动
- **结论**：非客户端 bug，是平台分块机制；跨边界后继续对话 2-3 轮应恢复全命中
- **已审计干净**：TimeReminder 基于固定消息时间戳注入；system 完全静态化（v3.3.6）；工具池请求内快照稳定
