# RinCore 方案决策记录

## D1. 传输层回滚到 3.2.2（v3.5.0，用户决策）
- **背景**：DeepSeek V4 Flash 连接中断反复出现（SETTINGS/reasoning/空流），v3.4.5-v3.4.10 连续补丁无法根治，用户判定"补丁式修改已没救"
- **决策**：传输层整体 checkout 3.2.2（原版 RikkaHub 2.4.5 移植前基线）
- **回滚文件**：OpenAIProvider/ChatCompletionsAPI/ResponseAPI/Message.kt/GenerationHandler/PlaceholderTransformer/PromptInjectionTransformer/ChatService
- **保留**：流式落盘（v3.4.6）、FGS 类型（v3.4.4）、AlarmScheduler DI（v3.4.2）、保活/权限/闹钟/工作流、MCP/域分类/工具路由
- **教训**：补丁累积会偏离原始架构——当问题反复出现时，回滚到已知稳定基线比继续打补丁更高效
- **代价**：3.2.2 时代工具池小，全量注入无感；现在 264 工具暴露 70K 注入问题（v3.5.1 修复）

## D2. 缓存策略（DeepSeek 前缀单元制）
- **机制**：每个缓存前缀是独立完整单元；后续请求必须完全匹配某单元；单元产生于请求边界/公共前缀检测/固定 token 间隔
- **推论**：system 是公共前缀始终命中（断后掉到 ~9.7K）；60K 附近跨单元边界会断；跨边界后 2-3 轮恢复
- **决策**：system 完全静态化（v3.3.6 移除 use_skill 动态注入）——动态注入会破坏公共前缀
- **矛盾记录**：v2.9.5"注入隔离"（BEFORE_SYSTEM_PROMPT 独立消息）为了缓存前缀稳定，却破坏协议（首条非 system）——缓存优化不能牺牲协议正确性
- **缓存门槛**（千问）：隐式缓存自动开启；Qwen3.7 ~2000 tokens 门槛；命中率非 100%；首次无缓存——非客户端可控

## D3. 注入隔离 vs 协议正确性（v2.9.5 → v3.4.5 → v3.5.0）
- **v2.9.5 决策**：BEFORE_SYSTEM_PROMPT 作为独立 user 消息（注入隔离，最大化前缀命中）——结果：首条非 system，严格端点报 SETTINGS
- **v3.4.5 修正**：合并进 system 开头（与既有测试期望一致）——协议正确优先
- **v3.5.0 回滚**：3.2.2 基线（合并语义）——协议正确性 > 缓存边际收益
- **结论**：协议合规（首条 system）是硬约束，缓存优化只能在硬约束内做

## D4. 闹钟功能去向（v3.4.3 用户决策）
- **选项**：默认开启 / 藏 UI / AI 工具管理
- **决策**：定时任务 AlarmManager 双通道默认开启（无需 UI 操作）；设备闹钟由 AI 工具管理（alarm_create/list/delete——fork 移植）；UI 入口移到"数据与存储"（不扎眼）
- **理由**：闹钟是用户意图驱动的（无人创建就是空表，"默认"无意义）；AI 管理符合助手定位；用户嫌设置页乱

## D5. 消息序列清洗策略（v3.3.13 → v3.5.0）
- **v3.3.13**：清洗移到循环内每步 + 移除所有未配对 tool_call（不只是末尾）——修复 SETTINGS 报错（孤儿 tool_call 残留）
- **v3.5.0 回滚**：3.2.2 基线（清洗在入口一次）——回滚后孤儿 tool_call 处理回到旧逻辑；若再遇 SETTINGS 需评估是否重移植
- **教训**：v3.3.13 的清洗强化本身合理（保留文本与已配对 tool_call），但作为补丁链一部分被整体回滚——重移植时只取验证过的部分

## D6. 工作流移植（阶段 3 未完成）
- **现状**：纯逻辑文件已搬运（DB/模型/动作定义）；Workflow.kt 裁剪（去 Capability 依赖）；TriggerRegistry 裁剪为 4 核心 family（Time/Manual/Boot/Battery）；WorkflowBootDispatcher 在 BootTrigger.kt 内
- **未完成**：WorkflowEngine 执行层重写（对齐 ToolExecutionContext/ToolCallOrigin）、UI 适配、MCP 工具集成、导航注册与设置入口
- **关键发现**：已有 DirectModeActionRunner（CronJobWorker 使用）→ 工作流动作可直接复用，执行层零适配；AgentRunKind.Workflow 已有

## D7. 保活链路设计（阶段 1）
- **核心结论**：定时任务不依赖进程存活——AlarmManager PendingIntent 注册在系统进程，app 被杀后到点系统重新拉起进程执行
- **链路**：系统闹钟唤醒（被杀也能触发）→ 前台服务执行（dataSync 类型，执行中不被打断）→ 结果落库
- **限制**：Android 系统层面"强制停止"后任何机制无法唤醒（需诚实说明）；澎湃 OS 墓碑/速冻不影响 AlarmManager 唤醒

## D8. 前台服务类型选择（v3.4.4）
- **选项**：dataSync vs specialUse
- **决策**：dataSync（ForegroundInfo 指定 + Manifest 覆盖声明 + 权限）——specialUse 需要 manifest property 且语义不符；dataSync 对定时任务执行语义匹配（6 小时限制对 1-2 分钟执行无影响）

## D9. 冷态 vs 版本回归 判定协议（2026-09-26 定版）
- **结论**：新装包首用慢 = **安装冷态**（JIT 未预热/后台 dexopt 未完成），与版本代码无关——反复装新包不断把热态清零，天然制造假回归（B47 实证）
- **协议**：任何版本 A/B 对比必须"热态判读"——装包后充分使用数分钟（反复滑动至手感稳定）再判流畅；跨版本对比=热态 vs 热态
- **配套**：探针包体系（diag-X.Y.Zp 单变量隔离）+ 阶梯二分（窗口压缩）

## D10. 预热管线 / 铺展架构（v4.8.50 用户定版）
- **原则**："用时间、空间换体验与效能"——瞬时高负载铺展开；解决不完的放进存储（Phase 3 设计在案）
- **三层**：①启动预热（2.5s 后最近对话 160 条）②会话进入预热（±80 条）③滚动停稳补热（debounce 1.2s 重铺）
- **硬约束**：只填充解析缓存，**可见渲染行为零变化**（连续性由原版形态保证）；分时切片；生成中避让；全链单飞
- **文档**：docs/WARM_PIPELINE.md；待做：Phase 3 存储沉淀（content-hash 磁盘 LRU）

## D11. 追赶线永久废弃（2026-09-26 用户定版）
- **范围**：4.8.36-41"渲染速度跟上模型输出速度"研究线——单飞行/自适应节流（"上轮耗时决定下轮节奏"）/合并窗口/"喘口气"/检查点
- **处置**：全部删除、**永不复用**；渲染链只允许"零行为变化"的纯 CPU 优化
- **警示**：任何"改变何时上屏"的方案进入候选前，先对照本条

## D12. 全量回植 / 不再开倒车（v4.8.48-49 用户定版）
- **原则**：4.7.26 之后的功能性改动**只进不退**；被误判为卡顿源而撤离的改动已全量回植
- **例外**：被新架构取代者不回植（全量预热 → 铺展管线 D10）; 被用户否决方向者不回植（渲染调度实验 D11）

## D13. CI 一推一建（2026-09-26 用户定版）
- **规则**：版本提交 push 到 main 即自动触发 build.yml——**禁止再手动 workflow_dispatch**（此前一版双跑：派发的"构建APK"+push 的提交标题运行）
- **例外**：诊断 tag 不在 push 触发范围（on.push 仅 main/master 分支），仍走 dispatch
- **完成判定**：CI 绿 = 定性完成（用户自行下载 Release APK）；诊断包同样轮询到终态

## D14. 保存链真实结果原则（v4.8.53）
- **原则**：用户可见的成功/失败提示**必须由真实结果驱动**——禁止"吞异常 + 无条件成功提示"的假成功
- **标准写法**：媒体库写入用 MediaStore 两段式（IS_PENDING 1→写→0，失败删占位行）；入口全链 Boolean 返回 + Log.i/Log.w 留痕

## D15. 工具矩阵统一模型（v4.8.83 用户定版）
- **背景**：旧「工具域」体系是 AI 早期应付式产物 —— 内置/自定义两套宇宙 + 9 个平行配置面，产生"删除假成功 / 空区蒸发 / 新建立刻被清理 / 移进域是死配置"等成串 bug。
- **决策**：**结构上消灭二元性**，而不是给每条路径打补丁。
  1. 单一数据模型：`ToolZone{id,title,description,keywords}`，**id（完整路径）即身份、创建后不可变**；无 parent 字段、无 normalizedFullPath、无四套寻址。
  2. **声明即存在**：工具区只要被声明就出现在矩阵里（0 工具也出现）；出厂模板仅首启播种一次，此后完全归用户。
  3. **兜底区 `未分类` 永远存在**（缺失即隐式补上）：保证 `Σ(区直接工具数) + 顶层直连数 == 工具池总数` 这条不变量恒成立。
  4. **顶层工具一个口径**：出厂模板 + 用户提升 − 用户降级；注入链直接消费它。
  5. **删除是真删除**，并明确迁移手动归属（父区优先，否则交回自动归类）。
- **代价/取舍**：① 工具区 id 不可改（改名只改显示名）—— 换取彻底消灭"双叠路径/幽灵区"这一整类 bug；② 后续版本新增的出厂工具区需用户点一次「恢复出厂工具区」（只增不删）—— 换取"用户删掉的区不会被自动复活"；③ 旧 `demotedFrameworkTools` 迁移时**丢弃**（保留实际行为）—— 需要把某工具移进工具区的用户在新界面点一次即可，这次是真生效。
- **原则**：出现"两条互斥规则需要同步维护"时，正解是**合并成一**，不是加分支。

## 决策原则（沉淀）
1. 协议合规 > 缓存收益 > 代码优雅
2. 用户决策优先（回滚/UI 取舍听用户的）
3. 补丁累积到反复失败时，回滚到稳定基线重来
4. 改代码先看既有测试期望（v2.9.5 偏离测试的教训）
5. 平台行为（缓存命中率/空流/清理机制）不可修复时，文档化并调整预期
6. 渲染调度只做"零行为变化"优化——任何改变"何时上屏"的改动必须极度谨慎（B46 教训）
7. 用户提示必须真实结果驱动——假成功是信任的致命伤（B51 教训）
8. 版本对比先排除安装冷态——连续装包测试流天然制造假回归（B47 教训）

## D16. 切换助手零导航（v4.8.111 用户二次定版）
- **背景**：用户两次反馈"切换助手后被拽回默认对话页"；v4.8.110 尝试"对话页跳目标会话 / 其它页停留"，用户实测真实路径在对话页 → 仍被拽走 → 明确否决。
- **决策**：**切换助手 = 只切助手、零导航**——任何页面（含对话页）切换助手都原地停留：不跳会话、不换页；仅收起小屏 Modal 抽屉（大屏常驻抽屉不动）。
- **影响面**：ChatDrawer AssistantPicker.onUpdateSettings（切换助手唯一 UI 入口；全库 navigateToChatPage 调用点已普查确认其余都是正常"跳去某会话"）；Navigator.current（v4.8.110 加的判据访问器保留备用）。
- **教训**：行为修复必须先确认用户真实操作路径（场景复述 + 全库入口普查），不能按想象路径改一半。

## D23 雾化方向翻底 + 标题栏整条雾化（含倒圆角）+ 连续曲率圆角（曲率梳平滑）（v4.8.180-dev 用户定版）
- **决策**：①雾化方向 = **下浓上淡**（0.7p 在下、0.15p 在上；"雾化从上半部分雾化变为下半部分雾化"）——输入栏与标题栏共用同一刷子；②**整条标题栏**（含状态栏内边距区）= 雾化面板 + 倒圆角：ChatPage topBar 槽位包 Box，面板铺满槽位、下方两角连续曲率圆角 20dp（顶边贴屏幕无法圆角；如需整体浮起四角全圆=加边距即可）；③**所有的圆角 = 曲率梳平滑（连续曲率 / G2）**：新件 `ContinuousCornerShape`（超椭圆 |x|^n+|y|^n=1 四分之一, n=4, 每角 24 段采样）——与直边衔接处曲率=0（直边也是 0）→ G2 连续；输入栏容器四角同半径切换（20dp = M3 largeIncreased, androidx 源取证）。
- **背景**：用户指令："雾化从上半部分雾化变为下半部分雾化，同时把整个标题栏也做成这种效果，并且倒圆角。就是把那个标题栏全部做成这效果。所有的圆角，这里是所有的圆角，现在还要用曲率梳梳出来。"
- **验收物**：曲率梳对照图 rin-corner-comb-v4.8.180.png（圆弧角 κ·r≡1.00 跳变 vs 连续曲率 0→2.52→0 平滑收束）。
- **待摊开**：其他组件（弹窗/卡片/气泡/按钮）如也要连续曲率圆角，说一声一处一行铺开（同件通用）。

## D22 开发者调试面板 + 开发者版本门控（v4.8.179-dev 用户定版）
- **决策**：①输入栏玻璃全部可用旋钮（半径/噪点/蒙版浓度/蒙版色/雾化/描边粗细/描边亮度）收进**主页面顶栏**的"开发者调试"面板（Bug 图标，位于"更多栏/新增对话"左侧），全部实时作用于真实输入栏；②该入口/面板由 `BuildConfig.DEVELOPER_BUILD` 门控——**仅开发者版存在，标准版没有**；③开发者版以 versionName 后缀 `-dev` 明确标注（Release = "RinCore v4.8.179-dev"）。
- **背景**：用户指令："在我明确标注的开发者版本中有的，在我标准使用版本中是没这个选项的。现在发一个开发者版本…把能用的选项都扔在那里，而且确定是要挑这个真实生效的。"
- **配套**：描边默认 1dp@纯白 → 0.5dp@55%（太粗太亮）；半径旋钮回归（2-24dp）；噪点层序=先噪点后模糊（S1 底层带噪点、S2 顶层纯模糊）。
- **标准版预案**：未来标准发布 = `DEVELOPER_BUILD=false` + versionName 去 `-dev` 后缀；其余（描边默认/层序）保留。

## D21 输入栏双层玻璃 = 串行再模糊 + 3dp 单模糊边；外观旋钮集齐（v4.8.178 用户定版）
- **用户指令**："第一层输出的再模糊一遍，然后输入栏再圈出来，深色模式用纯白线，边缘大约3dp只模糊一遍做层次，噪点参数范围大一点，还要有雾化我也试试，还有其他的，标题栏下移10dp。"
- **机制事实**：真"叠加"必须串行（第二层模糊第一层的输出）；并行叠两层（同样源各模糊一遍）≈ 一次（同一图像叠两次）= 假双层。串行等效 σ≈4dp×√2≈5.7dp，仍低于一切降档阈值（物理半径<32px）——"加深一档不出格栅"的正确通道。
- **落地**：S1 中间玻璃片（matchParentSize 与输入栏同槽位 → 天然对齐零坐标计算；hazeSource 捕获其单次模糊输出作为第二层的源）→ S2 再模糊一遍、内缩 3dp（边缘一圈只显单模糊=层次）。最差情形（第二层捕获失败）退化=单层模糊（良性失败，不会黑/不会坏）。
- **纪律**：半径仍恒 4dp（119 定版、不提供旋钮）；"更浓"只走串行结构与蒙版浓度，不走大半径（大半径=格栅域，见 B191/教训#101）。
- **外观三旋钮集齐**：噪点 0-100（默认 15=Material3 预设档，beta01 源码核实=零变化默认）/ 蒙版浓度+色（跟主题/深/浅）/ 雾化（白色柔雾 上浓下淡）——整组默认值复现改版前逐字节。

## D20 输入栏模糊 = RinFrost 自管高斯引擎（默认）+ 磨砂管线可回退（2026-10-17/18 用户定版）【已废弃 — v4.8.176 渲染层整体回滚 4.8.119】
- **决策**：输入栏玻璃默认走 **RinFrost 自管高斯**（BlurView 范式 Compose 实现：源捕获→1/8 降采样→CPU 盒式模糊×2 轮→双线性上采样；20fps 节流）；设置「模糊技术」可切回 haze 磨砂管线；D19 全旋钮映射保留。
- **判据（B188 用户实测收口）**：任何半径都有格栅、噪点 0 出、板压不住、Quality 全保真出 → 纹理在 GPU 模糊合成链内部，参数域已穷尽 → 换路线域。
- **边界**：全屏编辑器仍 haze（跨窗捕获另议）；自管路线无噪点旋钮效应（CPU 输出本就无网格）；模糊层数（夹心）仅磨砂管线参与。
- **⛔ 已废弃（v4.8.176）**：用户定版放弃本方案（真机黑屏大 bug + 用户否决自管路线），整个渲染层回滚 4.8.119；本条仅作历史存档。现行输入栏 = 4dp Material3 单层基座 + v4.8.178 双层结构（见 D21）。

## D19 输入栏玻璃 = 全参数用户自定 + 夹心结构实验面（2026-10-17 用户定版）
- **决策**：输入栏玻璃的全部管线参数收进 设置→通用偏好「输入栏玻璃」8 控件（半径/模糊层不透明度/噪点/模糊层数/板开关/板色/板浓度/板层数），实时作用于真实输入栏；用户自己在对话页实地逐参数排查，不再经实验场中转。
- **结构**：双层模糊（实验）=修饰链 `blur1 → drawBehind(板) → blur2` 夹心（零重排实现：Surface 底色在双层时透明，板由夹层 drawBehind 绘制）；板层数=N 层同浓度叠加（等效 1-(1-p)^N，单 Surface 实现零开销）。
- **原版复刻档**：半径12dp + 噪点15% + 层透明度100% + 板关 = 原版 2.5.6 Material3 预设逐字形态——用户可直接拨到该档做同条件对照（若原版配方在我们机器上仍出纹理而原版干净 → 差异在环境/内容层，配方层排除）。

## D18 输入栏玻璃 = 渲染器实验场 F 配方（2026-10-17 用户定版）
- **决策**：真实输入栏（主+全屏）玻璃 = **Material3 预设 + 4dp 半径 + 零噪点 + 模糊层透明度 90%**（调用点全保真 Quality），单一来源 `RinGlass.inputBlurStyle()`；chrome 族（弹窗/图标/工具条）保持 blurStyle() 12dp。
